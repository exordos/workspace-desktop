# Workspace Desktop

- `crates/workspace-core` содержит контекст Workspace, авторизацию и тесты жизненного цикла сессии.
- `crates/workspace-desktop` подключает системные адаптеры и содержит окно и компоненты GPUI.
- [Архитектура](docs/plans/workspace-desktop-architecture.md) и [контракт авторизации](docs/plans/modules/auth.md) описывают границы модулей.
- [Дорожная карта](docs/plans/workspace-desktop-roadmap.md) ведёт от текущего блока к сценариям, контрактам и карточкам задач.

## Разработка фич

При проектировании или реализации любой фичи используй [Workspace Desktop Feature](skills/workspace-desktop-feature/SKILL.md), даже если задача затрагивает только `workspace-core` или только `workspace-desktop`. До правок найди владельца поведения и проверь, что можно переиспользовать.

Для поэтапного переноса фичи из Electron используй [шаблон промпта и маршрут переноса](docs/agents/workspace-desktop-feature-port.md). Веди карточку фичи в плане блока и обновляй её по итогам итерации.

## Ревью

При ревью изменений или отдельного этапа используй [Workspace Desktop Review](skills/workspace-desktop-review/SKILL.md). Если делегируешь ревью, передай субагенту путь к этому скиллу, задачу, критерии этапа и точный diff.

Запускай `cargo check-architecture` из корня проверяемого checkout при изменениях в манифестах, Rust-коде на границе модулей или самом инструменте. Эту же команду используй в CI. [Правила проверки](docs/plans/roadmap/architecture-lint.md)

## Запуск приложения

Окно и команда `workspace-auth sync` используют общий запуск `workspace_core::bootstrap`. Порядок начальной загрузки описывай в [Bootstrap](docs/plans/workspace-desktop-architecture.md#bootstrap), а запросы, обработку и хранение данных оставляй в модуле, который ими владеет.

На macOS `cargo dev` подписывает каждую пересборку одним dev-сертификатом и открывает обычный профиль. Для самостоятельной проверки на стенде запускай `cargo dev --test-profile` с отдельным временным профилем без Keychain. [Настройка dev-запуска](docs/plans/modules/auth.md#dev-запуск-на-macos) описывает сертификат и тестовый вход. При первом запуске скрипт скачивает закреплённую версию `watchexec` в `target/dev-tools/` и проверяет SHA-256 архива. `Ctrl+C` останавливает наблюдение и клиент.

## Комментарии к коду

Пиши комментарии на русском простыми словами. Читатель без опыта в Rust должен понимать, зачем нужен код и что в нём происходит.

- Начинай каждый Rust-файл с короткого комментария `//!`. Объясни, зачем нужен файл, за что он отвечает и что читатель найдёт внутри. Если в файле несколько частей, перечисли их в порядке чтения.
- У каждой функции и метода добавляй короткий комментарий `///` о назначении, даже если имя говорит само за себя. Когда это помогает понять код, поясни, где или когда вызывать функцию, что она возвращает и что происходит при ошибке.
- У каждого типа и трейта объясняй, что он описывает и зачем нужен. У каждого поля структуры или варианта перечисления пиши короткий `//` справа от объявления на той же строке. Объясняй, что хранится в поле и как понимать его значение. Если важны единицы измерения или смысл `None`, укажи их там же.
- Внутри функций поясняй неочевидные решения и шаги. Обычно хватает одной-двух коротких фраз о том, зачем нужен этот шаг. Обновляй комментарии вместе с кодом.

## Работа с UI

- Новые экраны и компоненты реализуй на **GPUI**. Выбирай срез по [плану UI-паритета](docs/plans/roadmap/gpui-ui-parity.md). Границы рабочего клиента описаны в [архитектуре](docs/plans/workspace-desktop-architecture.md).
- Для проектирования, реализации или ревью компонентов и экранов используй [Workspace Desktop UI](skills/workspace-desktop-ui/SKILL.md).
- Когда для задачи нужен актуальный макет, используй [Workspace Desktop Figma Bridge](skills/workspace-desktop-figma-bridge/SKILL.md), даже если Figma не упомянута.

## Автотесты

При изменении поведения, исправлении бага или работе с автотестами используй [Workspace Desktop Testing](skills/workspace-desktop-testing/SKILL.md).

Для ручной проверки UI используй запущенный `cargo dev`, если он работает из нужного worktree, пересобрал последние правки и подходит по профилю и параметрам запуска. Для другого worktree или приёмки пакета используй сборку из нужного checkout. Переиспользуй `target` этого worktree для повторных прогонов. Созданный для задачи временный `target` убери после проверки и сохранения нужных журналов, если продолжение проверки его не требует. Подробности в [правилах запуска и сборки](skills/workspace-desktop-testing/SKILL.md#запуск-и-каталоги-сборки).

При разработке и отладке сценариев сверяйся с [правилами диагностических журналов](docs/plans/workspace-desktop-architecture.md#диагностические-журналы). По записям должно быть можно проследить действие пользователя до результата.

### Тестовые аккаунты

Для ручных проверок на тестовом стенде бери данные из `.env.test.local` в корне основного checkout репозитория. Git игнорирует этот файл, поэтому в отдельном worktree его может не быть.

- `WORKSPACE_TEST_URL` — базовый HTTPS-адрес организации.
- `WORKSPACE_TEST_LOGIN_A` и `WORKSPACE_TEST_PASSWORD_A` — логин и пароль первого аккаунта.
- `WORKSPACE_TEST_LOGIN_B` и `WORKSPACE_TEST_PASSWORD_B` — логин и пароль второго аккаунта.

Если тест читает переменные окружения, загрузи их в той же оболочке: `set -a; . ./.env.test.local; set +a` (из корня основного checkout). Не выводи значения паролей в логи и отчёты.

## Проверки из корня workspace

```sh
cargo check-architecture
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo test --workspace --no-default-features
cargo test -p workspace-desktop --features gpui-test --all-targets
```

[Запуск авторизации без окна](docs/plans/modules/auth.md#запуск-без-окна) описывает проверку на тестовом стенде. На macOS окно запускается командой `cargo run -p workspace-desktop --bin workspace-desktop`, галерея — `cargo run -p workspace-desktop --example ui_gallery`.
