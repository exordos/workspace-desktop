# Дорожная карта Workspace Desktop

Цель — настольный Workspace с мессенджером, почтой и календарём в общей оболочке. У разделов свои данные и синхронизация. Общая оболочка отвечает за сессии, навигацию и уведомления. [План проекта](workspace-desktop.md) · [Архитектура](workspace-desktop-architecture.md)

## Текущий этап

Первым доводим мессенджер до полного обмена сообщениями между двумя аккаунтами. В локальной ветке есть фундамент, фоновое получение и открытие истории, а также операции очереди отправки. Для входящего сценария нужна проверка на стенде и в настоящем окне macOS. Для исходящего — подключение очереди и редактора к рабочему чату. [Детальный план первого обмена](roadmap/messenger-first-loop.md)

Дальнейшие блоки и пилот на macOS — предлагаемый порядок. Состав пилота, обязательность E2EE для его участников и целевые платформы следующего выпуска нужно согласовать до постановки задач, которые зависят от этих решений.

## Блоки

| Блок | Зависимости | Результат блока и где его разбирать |
| --- | --- | --- |
| **Фундамент** | — | Два аккаунта независимо входят, восстанавливают сессии и обрабатывают события. Сбой или выход одного не затрагивает другого. Базовые механизмы уже есть, новые сценарии проверяют их на своих маршрутах. [План фундамента](workspace-desktop.md#фундамент-и-зависимости) · [Общие модули](features/foundation/index.md) |
| **Первый обмен сообщениями** | Фундамент | B получает сообщение в фоне, открывает его из уведомления и отвечает из чата. После обрыва или повторного события история сходится без дублей. [Входящие и отправка по шагам](roadmap/messenger-first-loop.md) |
| **Ежедневная работа в мессенджере** | Первый обмен. Отдельные сценарии можно проектировать после стабилизации их контрактов | Пользователь открывает личные чаты, каналы и темы, читает историю, управляет непрочитанным, продолжает черновик, отправляет вложение и выполняет согласованные действия над сообщением. [План ежедневных сценариев](roadmap/messenger-next.md#ежедневная-работа-в-мессенджере) |
| **Поставка и пилот** | Для сборки и диагностики достаточно фундамента. Для пилота нужна согласованная часть ежедневных сценариев | Пользователь устанавливает и обновляет сборку, восстанавливает сессию после перезапуска, получает системные уведомления. Команда повторяет проверку на целевой macOS и диагностирует сбой соединения. [Подготовка поставки и условия пилота](roadmap/pilot.md) |
| **Расширение мессенджера** | По сценарию. Папкам нужен каталог, активности — история и непрочитанное, опросам — редактор и отправка | Дополнительные ветки для навигации и архива, активности и поиска, опросов и интеграций. [План расширения](roadmap/messenger-next.md#расширение-мессенджера) |
| **Шифрование** | Контракты истории, отправки и владения ключами. Исследование совместимости можно начать раньше | Два клиента обмениваются защищённым сообщением. Доступ и состояние ключей проверяются отдельно для каждой сессии, включая смену устройства и выход. [План E2EE](roadmap/messenger-next.md#шифрование) |
| **Почта** | Общие сессии, оболочка и подтверждённый контракт почтового сервиса | Первый кандидат — открыть ящик и прочитать письмо в нужном аккаунте. [План почты](roadmap/sections.md#почта) |
| **Календарь** | Общие сессии, оболочка и подтверждённый контракт календаря | Первый кандидат — открыть расписание и событие нужного аккаунта. [План календаря](roadmap/sections.md#календарь) |
| **Звонки** | Контекст аккаунта, маршрутизация приглашений и подтверждённый контракт конференции | Первый кандидат — принять приглашение, подключиться с нужным аккаунтом и завершить звонок. [План звонков](roadmap/sections.md#звонки) |

## Как идти по плану

1. **Дорожная карта → блок.** Здесь выбираем ближайший результат, видим зависимости и открываем план блока по ссылке из таблицы.
2. **Блок → сценарий → контракт.** В плане блока фиксируем результат, порядок и независимые направления. Сценарий берём по постоянному ID из [каталога](features/README.md). Правила поведения и границы модулей уточняем в [контрактах](workspace-desktop-architecture.md#модули-и-ответственность).
3. **Сценарий → карточка.** Планировщик сверяет локальный HEAD, очередь и зависимости. Одна карточка даёт один результат с приёмкой. Ключ — `<ID>/<вид>/<короткий-срез>`. Карточка ссылается на блок, сценарий и контракт. Если остаётся вопрос к API или поведению, следующая задача может быть исследованием с конкретным вопросом и ожидаемым решением. [Инструкция планировщика](../agents/workspace-desktop-planner.md)
4. **Карточка → результат → следующий шаг.** Исполнитель оставляет в очереди SHA, результаты проверок и путь к принятому решению. Каталог хранит подтверждённый статус сценария. План блока обновляем, когда меняются зависимости, порядок или критерий готовности. [Инструкция исполнителя](../agents/workspace-desktop-executor.md)

Агенты могут брать независимые карточки параллельно, когда их обязательные зависимости уже в общей ветке, а изменения не пересекаются. Если две задачи меняют один экран, общий контракт или схему хранения, планировщик сначала выделяет общую зависимость либо ставит задачи последовательно. При приёмке блока отдельно сверяем тесты с моком, прогон на выделенном Workspace и проверку в окне ОС.
