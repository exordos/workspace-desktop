# Первый обмен сообщениями

[Дорожная карта](../workspace-desktop-roadmap.md) · [Исходный план первого этапа](../workspace-desktop.md#первый-сценарий-мессенджера)

Пользователь работает под аккаунтом A. Аккаунт B получает текстовое сообщение в существующем личном чате без E2EE. Из системного баннера пользователь открывает B у нужного сообщения и отвечает из этого же чата. Второй клиент получает ответ. Сбой сети и повтор события не создают дубликат и не меняют аккаунт или чат отправки.

## 1. Довести входящий сценарий

Фоновое получение, счётчик, открытие истории и прокрутка к цели покрыты локальным сценарием с Iced и тестовым сервером. Системную доставку баннера и фактическое восстановление окна проверяем отдельно. В рабочем дереве на момент составления плана есть правка повторного открытия истории после сброса. Перед декомпозицией сверь её состояние по HEAD и очереди.

| Шаг | Результат и проверка | Зависит от |
| --- | --- | --- |
| Восстановление открытого чата | При сбросе своего курсора открытая история скрывает старые строки и восстанавливается после повторной проверки доступа. При отозванном доступе старые данные не возвращаются. Сброс другого аккаунта не меняет экран. [SYNC-007](../features/foundation/sync.md#sync-007) | Текущая работа по сбросу. Продолжить существующую карточку или работу, если она уже начата. |
| Выделенный Workspace | Два аккаунта проходят существующий тест через настоящие REST и WebSocket. При входящем для B сохраняется маршрут A, счётчик B растёт один раз, приложение запрашивает уведомление для B. [MSG-READ-005](../features/messenger/unread.md#msg-read-005) · [Команда и условия](../workspace-desktop.md#сервер-для-интеграционных-тестов) | Два тестовых аккаунта, общий проект и личный чат с разрешёнными уведомлениями. |
| Баннер macOS | Для открытого и свёрнутого окна зафиксировать показ системного баннера, восстановление и фокус окна, выбор B, открытие личного чата и позицию у сообщения. [NTF-002](../features/foundation/notifications.md#ntf-002) · [MSG-HIST-004](../features/messenger/history.md#msg-hist-004) · [Ручной прогон](../modules/shell-platform.md#клик-по-баннеру-macos) | Те же тестовые условия, собранный пакет и интерактивная сессия macOS. |

## 2. Подключить отправку из чата

В `workspace-core` есть подготовка и сохранение записи, первая попытка с захватом записи, подтверждение доставки и поиск сообщения по публичному UUID. Редактор доступен как компонент UI kit. Следующие шаги связывают очередь с фоновой работой и интерфейсом. [Контракт отправки](../modules/messenger-send.md)

| Шаг | Результат и проверка | Зависит от |
| --- | --- | --- |
| Фоновая попытка для записи очереди | Сохранённая запись уходит по адресу исходного чата с сессией владельца. Смена видимого аккаунта не влияет на отправку. Одновременное пробуждение или повторный запуск не создают второй первый POST. [MSG-COM-012](../features/messenger/composer.md#msg-com-012) | Сохранение подготовленного сообщения и атомарный захват первой попытки. |
| Ввод и постановка в очередь | В открытом личном чате пользователь вводит текст и нажимает «Отправить». Текст очищается после успешной записи в очередь, а при ошибке записи остаётся в редакторе. Поздний ответ не очищает редактор другого чата. [MSG-COM-011](../features/messenger/composer.md#msg-com-011) | Согласованный вызов постановки в очередь. Проверка до доставки может использовать локальную очередь. |
| Подтверждение и состояния доставки | Подтверждённое сообщение заменяет ожидающую строку с тем же публичным UUID. HTTP-ответ и событие в любом порядке дают одну запись. При ошибке интерфейс показывает состояние, соответствующее исходу. [MSG-COM-013](../features/messenger/composer.md#msg-com-013) · [MSG-COM-014](../features/messenger/composer.md#msg-com-014) | Подключённые очередь, редактор и фоновая попытка. |
| Восстановление после потери ответа | После обрыва или перезапуска сверяем доставку по сохранённому UUID и событию. Неизвестный исход виден пользователю. Повтор POST разрешён только в случаях, подтверждённых [контрактом](../modules/messenger-send.md#обрыв-сети-и-повтор). [MSG-COM-014](../features/messenger/composer.md#msg-com-014) | Подключены сверка и состояния доставки. Если нужен неподтверждённый режим повтора, сначала выяснить его контракт на целевом сервере. |

## Порядок для агентов

- Проверку входящих на стенде и системного баннера можно готовить независимо от фоновой отправки. Если тесты используют одни и те же аккаунты и чувствительны к счётчикам, согласуйте время прогона.
- Фоновую попытку и ввод можно разбирать параллельно после фиксации вызова постановки в очередь. Перед публикацией карточек сверить файлы и общие контракты. Совместное изменение истории и её общей модели планировать последовательно.
- Использовать существующий ключ задачи при продолжении работы. Указанные ID — ссылки на сценарии каталога. Планировщик сверяет фактические карточки, HEAD и критерии перед созданием нового ключа.

Блок завершён, когда два аккаунта проходят весь обмен на выделенном Workspace, включая клик по баннеру в настоящем окне, а локальные проверки воспроизводят сброс истории, потерю ответа и повтор события. В результатах указываем SHA и подтверждённую среду для каждой проверки. Следующий предлагаемый блок — [ежедневная работа в мессенджере](messenger-next.md#ежедневная-работа-в-мессенджере).
