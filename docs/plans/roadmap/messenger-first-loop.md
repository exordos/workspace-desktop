# Первый обмен сообщениями

[Дорожная карта](../workspace-desktop-roadmap.md) · [Исходный план первого этапа](../workspace-desktop.md#первый-сценарий-мессенджера)

Пользователь работает под аккаунтом A. Аккаунт B получает текстовое сообщение в существующем личном чате без E2EE. Из системного баннера пользователь открывает B у нужного сообщения и отвечает из этого же чата. Второй клиент получает ответ. Сбой сети и повтор события не создают дубликат и не меняют аккаунт или чат отправки.

## 1. Довести входящий сценарий

Локальный тест уже проходит путь от входящего события по WebSocket до записи в SQLite, бейджа B и одного запроса на уведомление. Тест передаёт цель оболочке и проверяет, что история нужного чата открывается у сообщения. Два оставшихся уровня приёмки — настоящий REST и WebSocket выделенного Workspace и системный баннер в окне macOS. [Общий сценарий с моком и стендом](../workspace-desktop.md#сервер-для-интеграционных-тестов)

### 1.1. Проверить восстановление истории после сброса курсора

**Зависимость.** Сброс данных источника в `core::sync` и повторное открытие видимой истории в оболочке. На `051ba49` реализация и проверки уже в ветке. Если проверки обнаружат пробел, продолжаем работу по этому же сценарию. [SYNC-007](../features/foundation/sync.md#sync-007)

1. Проследить путь от отклонения курсора по WebSocket до `SyncChange::MessengerReset`. `Sync::reset_source` очищает данные владельца, затем оболочка сопоставляет событие с контекстом и поколением открытого входа.
2. Проверить, что оболочка сразу скрывает прежние строки, сбрасывает состояние догрузки и повторно проверяет доступ через `open_direct_history`. Ответ загрузки принимается только для актуального перехода и входа.
3. Переиспользовать тесты `local_wss_recovers_pruned_cursor_and_changed_epoch` и `background_message_updates_iced_badge_and_notifies_once`. В первом проверяем новый курсор и серверный счётчик B с сохранением данных A. Во втором заставляем мок сменить текст цели и отклонить курсор, затем проверяем, что открытая история показывает новый текст из REST. [Сброс в core](../../../crates/workspace-core/src/sync.rs) · [Сброс в оболочке](../../../crates/workspace-desktop/src/shell.rs) · [Тесты входящих](../../../crates/workspace-desktop/src/shell/background_message.rs)

**Приёмка.** Сброс B убирает старый текст сразу и возвращает только свежий после проверки доступа. Если чат отозван или сообщение исчезло, видна соответствующая ошибка без старого текста. Событие другого аккаунта или поколения и поздний ответ прежнего перехода экран не меняют.

```sh
cargo test -p workspace-desktop --lib local_wss_recovers_pruned_cursor_and_changed_epoch
cargo test -p workspace-desktop --lib background_message_updates_iced_badge_and_notifies_once
```

### 1.2. Проверить фоновое получение на выделенном Workspace

**Зависимость.** Два тестовых аккаунта в одном проекте и существующий личный чат Workspace без E2EE с включёнными уведомлениями для B. Во время прогона в обоих аккаунтах только тест меняет счётчики. [MSG-READ-005](../features/messenger/unread.md#msg-read-005)

1. Переиспользовать `background_message_scenario` с адаптером `LiveWorkspace`. Тест сам создаёт временный профиль, восстанавливает два входа и ждёт начальных счётчиков через штатную синхронизацию.
2. Задать адрес стенда, UUID проекта `WORKSPACE_TEST_PROJECT` и данные A/B по инструкции к сценарию. Из корня основного checkout загрузить `.env.test.local` в оболочке запуска. Значения секретов в отчёт не включать.
3. Запустить явный стендовый тест. Он отправляет из A уникальное тестовое сообщение, проверяет сохранение сообщения у B, фиксирует ровно один запрос на уведомление, затем передаёт его цель оболочке и проверяет открытие истории. [Условия теста](../workspace-desktop.md#сервер-для-интеграционных-тестов) · [Адаптер LiveWorkspace](../../../crates/workspace-desktop/src/shell/background_message/live.rs)

**Приёмка.** До клика выбран A и его счётчик прежний, B получил +1 и один запрос на уведомление с правильным аккаунтом, чатом и UUID сообщения. После передачи цели Iced открывает B у этого сообщения. Фактический показ баннера проверяется следующим шагом.

```sh
set -a
. ./.env.test.local
set +a
cargo test -p workspace-desktop --lib live_workspace_background_message_updates_iced_badge_and_notifies_once -- --ignored
```

Разрешить баннеры Workspace Desktop и проверить режим фокусирования. **Приёмка.** В обоих прогонах macOS реально показала баннер, приложение вышло на передний план, в случае свёрнутого окна развернулось, получило фокус и открыло нужное сообщение в личном чате B. В отчёте зафиксированы показ, клик, фокус и позиция в истории для каждого прогона.

## 2. Подключить отправку из чата

В `workspace-core` уже есть запись до POST, атомарный захват первой попытки, одноразовые POST и GET для сверки и транзакции подтверждения. В Desktop есть редактор и пузырь сообщения в UI-ките. До полного обмена нужно связать эти операции с жизненным циклом сессии и экраном. Первый срез отправляет обычный текст в существующем личном чате. [Контракт отправки](../modules/messenger-send.md)

### 2.1. Разрешить точный адрес отправки в личном чате

**Основание.** `HistoryScope` личного чата содержит UUID стрима, а `Sync::prepare_send` нужен явный UUID темы. Каталог сворачивает темы лички, поэтому из строки списка целевой темы не получить. В `workspace_ui@af099988` маршрут стрима отправляет только в подтверждённую тему по умолчанию. [Чтение доступа](../../../crates/workspace-core/src/messenger/rest.rs) · [Каталог](../../../crates/workspace-core/src/messenger/catalog.rs) · [Выбор цели в референсе](../../../../workspace_ui/packages/web/src/pages/chat/chat-page-workspace.ui.tsx)

**Реализация.**

1. В `core::messenger` переиспользовать проверку личного стрима через `GET /streams/{uuid}`. Из подтверждённого ответа взять `default_topic_uuid` и связать пару UUID стрима и темы с владельцем и поколением сессии. В ревизии backend `bc986e0` поле входит в модель публичного ресурса стрима, а GET возвращает эту проекцию с ограничением по контексту. Сверить поле и его доступность для B на целевом стенде перед сквозным прогоном. [Публичная модель](../../../../workspace_backend/workspace/messenger_api/dm/base.py#L463) · [Получение ресурса](../../../../workspace_backend/workspace/messenger_api/api/v2_store.py#L182)
2. Передать адрес в активный экран разговора отдельно от области чтения. История по-прежнему открывается для всего личного стрима, редактор отправляет в явную тему. Включать обычную отправку только для подтверждённого личного разговора без E2EE. Если поле темы отсутствует, пусто или некорректно, показать причину недоступности отправки. Сохранить доступ к уже открытой истории при ошибке определения цели. Запоздавший результат старого маршрута или поколения игнорировать.

**Приёмка.** Локальный REST-стенд отдаёт личный стрим с темой по умолчанию, отличной от темы последнего сообщения, и редактор получает тему по умолчанию. Для пустого чата при корректном поле редактор доступен, при пропущенном поле, чужом проекте, E2EE или устаревшей сессии отправка недоступна. Расширить проверки доступа из `cargo test -p workspace-core --test auth_lifecycle direct_history::`.

### 2.2. Запустить первую попытку из очереди для активных сессий

**Зависимости.** Уже есть `Storage::pending_sends`, `claim_first_send` и `MessengerSource::post_prepared_message`. Фоновую задачу можно проверить на подготовленных записях параллельно с подключением редактора. [Хранилище очереди](../../../crates/workspace-core/src/storage/outbox.rs) · [Транспорт отправки](../../../crates/workspace-core/src/messenger/send.rs) · [Bootstrap](../workspace-desktop-architecture.md#bootstrap) · [MSG-COM-012](../features/messenger/composer.md#msg-com-012)

**Реализация.**

1. Добавить обработку очереди в модуль мессенджера и подключить её через общий запуск `bootstrap`. Привязать обработчик к жизненному циклу сессии в `runtime`. При активации каждой сессии читать очередь её владельца, после успешной новой записи будить обработчик исходного контекста. Окно и `workspace-auth sync` используют тот же жизненный цикл, запросы принадлежат мессенджеру. Остановка и выход отменяют работу соответствующей сессии.
2. Получить токен мессенджера для владельца и поколения. Если до захвата уже известно, что сессия или соединение недоступны, оставить запись ожидающей. Повторить обработку с паузой или при восстановлении соединения. Состояние соединения, если оно уже доступно в `runtime`, использовать до захвата. Оно не меняет результат уже начатого POST.
3. Проверить актуальность поколения при захвате. Только результат успешного `claim_first_send` разрешает один POST с неизменным снимком, вне транзакции SQLite. Сетевую ошибку после начала POST считать неизвестным исходом. Сохранённые захваты после перезапуска передавать на сверку по задаче 2.5, остальные результаты обрабатывать по задаче 2.4.

**Приёмка.** В интеграционном тесте с локальным HTTPS-сервером активны A и B, запись принадлежит B. Повторные сигналы обработки при задержанном ответе дают один POST с токеном и точным адресом B. Отдельно проверить запуск с уже сохранённой записью, временный сбой до захвата и выход B без записи результата старого поколения. Переиспользовать фикстуры из `cargo test -p workspace-core --test send_message` и проверку `cargo test -p workspace-core first_send_claim_survives_reopen_and_preserves_legacy_pending`.

### 2.3. Сохранить сообщение из редактора открытого чата

**Зависимости.** Подтверждённый адрес из задачи 2.1 и существующий `Sync::prepare_send`. До подключения фонового работника сценарий проверяется по записи SQLite. [Экран истории](../../../crates/workspace-desktop/src/shell/history.rs) · [Редактор](../../../crates/workspace-desktop/src/ui_kit/message_composer.rs) · [Подготовка записи](../../../crates/workspace-core/src/sync.rs) · [MSG-COM-011](../features/messenger/composer.md#msg-com-011)

**Реализация.**

1. Подключить `message_composer` к открытому разговору. Экран хранит текст и версию ввода, UI-кит передаёт события. Для отправки проверить непустой текст и лимит референса `40 000` кодовых точек Unicode, затем зафиксировать владельца, маршрут, поколение, версию текста и номер перехода. Пока запись этого снимка выполняется, блокировать повторную отправку того же текста.
2. Передать снимок в `core` через `Sync::prepare_send`. Очистить отправленный текст только после успешного сохранения, если маршрут, поколение и версия совпадают. При ошибке оставить текст для повтора. При вводе нового текста или переходе в A результат для B может обновить его очередь, а редактор текущего экрана сохраняет свой текст. Запись и синхронизация черновиков на диске относятся к отдельному сценарию. [Лимит в Workspace UI](../../../../workspace_ui/packages/web/src/shared/lib/workspace-message-limits.lib.ts) · [Версия черновика](../modules/messenger-drafts.md#что-происходит-после-отправки)

**Приёмка.** Тест Iced нажимает штатную кнопку отправки. Для непустого текста и подтверждённой цели появляется одна запись очереди B, поле очищается после записи. Проверить пробелы, превышение лимита, сбой SQLite, двойной клик, изменение текста и переключение аккаунта до завершения записи. Переиспользовать рендерер и сценарий из [тестов оболочки](../../../crates/workspace-desktop/src/shell/background_message.rs), проверку поколения из `cargo test -p workspace-core --test auth_lifecycle prepared_send_is_persisted_only_for_active_session`.

### 2.4. Показать временную строку и согласовать подтверждения

**Зависимости.** Снимок очереди, редактор и фоновая попытка. `Storage::confirm_http_send` и обработка `message.created` уже закрывают совпавшую запись транзакцией. `Sync::confirm_http_send` пока не публикует обновление для окна, а экран истории рисует только подтверждённые сообщения. [Транзакция подтверждения](../../../crates/workspace-core/src/storage/outbox.rs) · [Пузырь сообщения](../../../crates/workspace-desktop/src/ui_kit/message_bubble.rs) · [MSG-COM-013](../features/messenger/composer.md#msg-com-013) · [MSG-COM-014](../features/messenger/composer.md#msg-com-014)

**Реализация.**

1. После сохранения показать временную строку с публичным UUID в истории нужного владельца и чата. Передавать в UI состояние очереди, попытки, серверного подтверждения, отказа или неизвестного исхода из мессенджера. Переиспользовать стили исходящего пузыря. Подтверждение означает приём сообщения сервером.
2. Перед фиксацией HTTP-ответа сверить публичный UUID, стрим, тему, автора и актуальность поколения с отправленным снимком. Использовать существующее подтверждение, затем оповестить экран о зафиксированном изменении. Для `message.created` и REST-догрузки событий оставить подтверждение в транзакции с курсором. HTTP курсор не меняет. Учитывать закрытие записи очереди, даже когда сообщение уже было в истории и новая строка в SQLite не вставилась.
3. Перечитывать подтверждённое окно и очередь в контексте владельца. При совпадении UUID оставить одну строку и сохранить актуальную правку или удаление. Если подтверждение за границей окна, применить существующую загрузку актуального хвоста при переходе к новым сообщениям. Временная строка сама по себе не подтверждает непрерывность истории. [Согласование событий и страниц](../modules/storage.md#как-сводим-страницы-истории-и-события)

**Приёмка.** Оба порядка, HTTP → `message.created` и `message.created` → HTTP, дают одну запись и одну строку. Повтор события и ответы прежней сессии не возвращают старое состояние. Проверить ответ с чужим автором или размещением, подтверждение вне окна и более свежие правку или удаление. Переиспользовать `cargo test -p workspace-core outbox_confirmation_is_atomic_and_preserves_newer_history` и добавить проверку результата в Iced.

### 2.5. Восстановить отправку после неизвестного исхода

**Зависимости.** Обработка очереди и обновления статуса из задач 2.2 и 2.4. `Storage::claimed_sends` читает сохранённые захваты, `MessengerSource::lookup_prepared_message` уже сверяет UUID, автора и адрес. Текущая схема хранит признак захвата, но не различает неизвестный исход и окончательный отказ после запуска. [Обрыв сети и повтор](../modules/messenger-send.md#обрыв-сети-и-повтор) · [Проверка контракта повтора](../modules/messenger-send.md#проверка-контракта-повтора)

**Реализация.**

1. Сохранять однозначный отказ и неопределённый исход раздельно. При изменении схемы оставить ожидающие записи ожидающими, а ранее захваченные без подтверждения восстанавливать для сверки. Неизвестный исход остаётся видимым после смены окна и перезапуска.
2. Если сессия B доступна, после неизвестного исхода запланировать сверку с паузой. После запуска или переподключения учесть события с сохранённого курсора. Пока подтверждения нет, выполнить GET по публичному UUID. Совпадение провести через тот же путь подтверждения с проверкой поколения. При отсутствии записи или ошибке GET оставить статус неизвестным. После ограниченного числа попыток ждать следующего события, активации сессии или переподключения. Однозначный отказ останавливает автоматическую отправку.
3. Повторный POST для уже захваченной записи включать только после отдельной проверки версии и конфигурации целевого сервера по контракту. Если повтор подтверждён и входит в срез, использовать сохранённый снимок. В POST передавать тот же канонический UUID, исходный стрим, явную тему и тот же payload. Публичный UUID остаётся ключом сверки. Сериализовать ручной и фоновый запуск для одной записи. Пока контракт не подтверждён, успешное восстановление проверять через события или GET без повторного POST.

**Приёмка.** Мок принимает POST и теряет ответ. Подтвердить сообщение событием, а в отдельном прогоне через GET при продолжающем работать соединении без новых событий. Повторить с перезапуском между захватом и ответом. На сервере один POST, в истории одна строка, ожидание снято. Если GET ничего не нашёл и события нет, состояние остаётся неизвестным, нового POST нет. Для окончательного отказа показать ошибку и проверить остановку автоматической отправки после восстановления сессии. Переиспользовать `cargo test -p workspace-core --test send_message` и тест с временным профилем для проверки перезапуска.

## 3. Проверить полный обмен в окне macOS

**Зависимости.** Проверены входящий сценарий и системный переход. Подключены редактор, очередь, сверка доставки и восстановление после обрыва. Для прогона нужен пакет с этими изменениями, два тестовых аккаунта и второй клиент на выделенном Workspace. [Сборка и профиль](pilot.md) · [Условия стенда](../workspace-desktop.md#сервер-для-интеграционных-тестов)

1. Открыть A в Desktop и отправить из второго клиента сообщение от A к B с уникальной меткой. Проверить счётчик B и переход из баннера к этому сообщению в контексте B.
2. Ответить из открытого разговора. Проверить доставку во втором клиенте и одну итоговую строку в Desktop. Затем отключить сеть, дождаться, пока фоновая работа определит недоступность соединения, и поставить новый ответ в очередь до первой попытки. Переключиться на A и вернуть соединение. Сообщение должно уйти в исходный чат B.
3. Зафиксировать SHA сборки, версию macOS, среду и результат каждого шага. Потерю ответа после записи на сервере, перестановку HTTP и WebSocket и повтор события подтвердить управляемыми локальными тестами из плана отправки.

Блок закрывается, когда в настоящем окне проходит обмен в обе стороны и локальные проверки подтверждают восстановление и отсутствие дублей. [Приёмка первого обмена в пилоте](pilot.md#приёмка-сборки-для-пилота)

## Порядок для агентов

- Проверку входящих на стенде и системного баннера можно готовить независимо от фоновой отправки. Если тесты используют одни и те же аккаунты и чувствительны к счётчикам, согласуйте время прогона.
- Фоновую попытку и ввод можно разбирать параллельно после фиксации вызова постановки в очередь. Перед публикацией карточек сверить файлы и общие контракты. Совместное изменение истории и её общей модели планировать последовательно.
- Использовать существующий ключ задачи при продолжении работы. Указанные ID — ссылки на сценарии каталога. Планировщик сверяет фактические карточки, HEAD и критерии перед созданием нового ключа.

Список чатов и первый обмен стыкуются в общем маршруте разговора. Для первого обмена достаточно входа из уведомления. [Мини-этапы списка](../workspace-desktop-roadmap.md#ближайшие-мини-этапы-списка-чатов)
