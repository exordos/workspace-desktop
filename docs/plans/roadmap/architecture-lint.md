# Архитектурные проверки Workspace Desktop

Согласованный первый срез. [Архитектурные границы](../workspace-desktop-architecture-rules.md) описывают владельцев и допустимые связи. Здесь фиксируем, какие нарушения можно определить по исходникам, какие требуют сборки или прогона и как подключить проверку к разработке и ревью.

## Что может проверить линтер

Ближайшая аналогия из TypeScript — `no-restricted-imports` для пары «где написана ссылка и к чему она ведёт», а для графа связей между частями приложения — dependency-cruiser. В Rust `use` только вводит имя в область видимости. Тот же доступ может быть записан полным путём в вызове или типе, а `pub use` может открыть путь через другой модуль. Проверять можно также декларации Cargo, видимость и форму вызова. Для каждого правила нужно назвать точный объект проверки. [ESLint](https://eslint.org/docs/latest/rules/no-restricted-imports) · [dependency-cruiser](https://github.com/sverweij/dependency-cruiser) · [Rust Reference](https://doc.rust-lang.org/reference/visibility-and-privacy.html)

| Уровень | Что видит | Пример для проекта |
| --- | --- | --- |
| Пакеты Cargo | Прямые декларации зависимостей, их типы, переименования, `cfg`, features и targets. При разрешении зависимостей — также транзитивный граф. | Проверить, что `core` не объявляет GPUI даже под другим именем или под `cfg(target_os = "macos")`. |
| Исходный код и граф ссылок | `use`, `pub use`, прямые пути в типах и выражениях, вложенность модулей, объявленную видимость и синтаксис вызовов. Граф можно сворачивать до файлов или слоёв. | Запретить `rusqlite::Connection::open(...)` в экране даже без `use`. Найти прямой вызов конкретного конструктора вне перечисленных точек входа. |
| Анализ на уровне компилятора | В выбранной сборке можно получить сведения о разрешённых именах, типах и коде после раскрытия макросов. Покрытие зависит от того, какие сборки запущены и что реализовано в правиле. | Определить, какой метод фактически вызван у значения, если из записи `value.open(...)` этого не видно. |

Clippy даёт готовые правила `disallowed_methods`, `disallowed_types`, `disallowed_macros` с уровнями линта по областям кода. | Сохраняем штатные проверки. Ограничения Clippy подходят для известных методов, типов или макросов. Матрицу «модуль-источник → модуль-цель» пришлось бы поддерживать через конфигурацию и атрибуты. Ссылки между Rust-файлами проверяет отдельный инструмент. [Cargo](https://doc.rust-lang.org/stable/cargo/commands/cargo-metadata.html) · [cargo-deny](https://embarkstudios.github.io/cargo-deny/) |

Есть правила размещения, циклов и отчёт о рёбрах. | Версию `0.0.2` проверили на stable. Она подходит для инвентаризации, а её трактовка `cfg(test)` не подходит для первого правила SQLite. [Документация и ограничения](https://github.com/dragonsec-ai/ArchUnitRust#known-limitations) · [Манифест](https://github.com/dragonsec-ai/ArchUnitRust/blob/main/Cargo.toml) |

Для нашей политики допустимых направлений понадобились бы дополнительные правила. [cargo-modules](https://github.com/regexident/cargo-modules#acyclic-mode) |
| `ast-grep` или свой обход через `syn` | `ast-grep` сопоставляет шаблоны с узлами синтаксического дерева. `syn` даёт Rust AST, который можно обойти своим кодом. Связывание имён между файлами потребует отдельной логики. | Для первого правила SQLite выбрали `syn`. При обходе можно исключать заведомо тестовый код и учитывать рабочие объявления `mod` и `#[path]`. [ast-grep](https://ast-grep.github.io/advanced/faq.html) · [syn](https://docs.rs/syn/2.0.117/syn/visit/index.html) |
| Semgrep | Выполняет правила по шаблонам кода. Анализ потоков данных в Rust ограничен одной функцией в Community Edition. Semgrep Code добавляет анализ между функциями. | Подходит для локальных правил о форме вызова или потоке данных. Для политики связей Cargo и модулей нужен граф проекта. [Матрица поддержки Semgrep](https://docs.semgrep.dev/semgrep-ce-languages) |
| `cargo-pup` и Dylint | Оба запускают анализ через внутренние API компилятора. У `cargo-pup` есть готовые ограничения импортов, видимости и элементов. Dylint запускает собственные Rust-линты. | Кандидаты, если понадобится проверять конкретный разрешённый символ или тип после раскрытия макросов. У `cargo-pup` правило `restrict_imports` проверяет `use`, поэтому прямой вызов через полный путь оно само не покроет. Понадобится отдельный закреплённый nightly и сборка нужных конфигураций. [cargo-pup](https://github.com/DataDog/cargo-pup#how-it-works) · [Реализация `restrict_imports`](https://github.com/DataDog/cargo-pup/blob/main/cargo_pup_lint_impl/src/lints/module_lint/lint.rs#L778-L838) · [Dylint](https://github.com/trailofbits/dylint) |

Первый срез использует `cargo metadata` и узкий обход исходников на `syn`. Проверку можно запускать отдельно от сборки приложения. Текущий репозиторий использует [stable](../../../rust-toolchain.toml).

## Что проверяем в первом срезе

| Проверка | Нарушение | Допустимый случай |
| --- | --- | --- |
| **ARCH-01 / зависимости crates** | `core` объявляет прямую зависимость от `workspace-desktop`, `gpui` или одного из нативных пакетов первого среза (`block2`, `objc2`, `objc2-app-kit`, `objc2-foundation`, `objc2-user-notifications`, `security-framework`). Нарушением считаются также отсутствие библиотечной цели ядра и отсутствие обязательной связи Desktop с локальным ядром из этого workspace. | `desktop → core`, включая переименование локальной зависимости. Прямые GPUI и нативные адаптеры в Desktop. Cargo читает исходное имя, вид и условие платформы. Транзитивные зависимости вне области этой проверки. [Манифест Core](../../../crates/workspace-core/Cargo.toml) · [Манифест Desktop](../../../crates/workspace-desktop/Cargo.toml) |
| **ARCH-01 / запуск без окна** | В метаданных нет одного из двух бинарников, окно перестаёт требовать `gpui`, у `workspace-auth` появляются `required-features` или зависимость Desktop от `gpui` перестаёт быть optional. | Штатное окно с GUI и CLI без default features. Декларации проверяют метаданные. Компиляцию CLI проверяет `cargo check -p workspace-desktop --no-default-features --bin workspace-auth`. Фактическое отсутствие GPUI, в том числе транзитивного, проверяется отдельно по разрешённому графу без default features на macOS. [Манифест Desktop](../../../crates/workspace-desktop/Cargo.toml) · [Запуск без окна](../modules/auth.md#запуск-без-окна) |
| **ARCH-08 / драйвер SQLite** | Прямая зависимость исходника от `rusqlite` вне `workspace-core/src/storage.rs` и `workspace-core/src/storage/` в коде приложения. Примеры — `use`, `pub use`, прямой путь в типе или вызове. | Прямой доступ в `storage`, намеренный доступ из тестов и штатные типы `core::storage` в UI. CLI и GPUI-воркер могут открыть `Storage` при сборке зависимостей. [Хранилище](../modules/storage.md) · [Тест отзыва доступа](../../../crates/workspace-core/tests/support/catalog_revocation.rs) |

**Уже проверяет компилятор.** Для ARCH-03 приватные модули, например `messenger::rest` и `messenger::socket`, остаются закрыты средствами Rust. Отдельный линт нужен, только если решим закрепить конкретный фасад или запретить расширение видимости перечисленных внутренних API. [Модуль мессенджера](../../../crates/workspace-core/src/messenger/mod.rs)

## Что можно проверить после уточнения границ

| Правила | Что можно автоматизировать | Что нужно уточнить |
| --- | --- | --- |
| ARCH-02 | Проверить, что штатные точки входа ссылаются на `bootstrap`. Искать отдельные запрещённые вызовы в Bootstrap. | Какие точки входа и операции входят в правило. Само наличие вызова не подтверждает, что вся ветка запуска до него доходит. |
| ARCH-03, ARCH-04 | Запретить прямые ссылки в конкретные внутренние подмодули, ограничить `pub use`, проверить циклы между выбранными группами файлов. | Какие публичные операции считаются фасадом. Сейчас контракт допускает прямые типизированные вызовы между владельцами. |
| ARCH-05, ARCH-06, ARCH-10, ARCH-13 | Проверить размещение конкретного адаптера или вызовы выбранного клиента, например SDK Keychain либо сетевого конструктора. | Указать разрешённые места и отличить вызов транспорта от использования типа вроде `reqwest::Url`. Учесть тестовый профиль, локальный тестовый сервер и существующие адаптеры окна. |
| ARCH-08, ARCH-09, ARCH-11, ARCH-12 | Проверить, что выделенные UI-примитивы не вызывают `Storage::open`, сетевой клиент или команды фоновой работы. Поимённо ограничить обращение к реализации справочника. | Описать границу между UI-примитивами, шапкой, экранами и точками сборки. Общие типы истории и профиля уже используются в UI. |
| ARCH-14 | Найти конкретный запрещённый вызов логирования или проверить обязательное поле в заданном макросе диагностики. | Выбрать общий API и измеримое правило. Наличие `op_id` в одном вызове не подтверждает, что идентификатор проходит через весь сценарий. |

## Что проверяем тестами и на ревью

| Гарантия | Как проверяем |
| --- | --- |
| Правильный владелец поведения и один путь операции из разных экранов или разделов (ARCH-02–04, ARCH-09–12). | На ревью проследить маршрут до реальной операции. Тестом проверить штатные точки входа и итоговое состояние. |
| Изоляция аккаунтов и поколений, один refresh, безвредный поздний ответ, остановка фоновой задачи (ARCH-05–07). | Подать управляемые события двух аккаунтов, задержать ответ, выполнить выход и переподключение. Проверить данные и наблюдаемое завершение. |
| Данные и курсор фиксируются одной транзакцией, повтор события и повтор отправки не дают дублей, отзыв доступа закрывает защищённый кэш (ARCH-07, ARCH-08, ARCH-10). | Проверить сбой и откат записи, повтор доставки, отзыв и повторное открытие, сопоставить данные и курсор на выходе. |
| Поздний результат не меняет другой маршрут, уведомление открывает нужный аккаунт и объект, фокус и прокрутка сохраняются (ARCH-11–13). | Проверить сценарии GPUI и реальные переходы ОС там, где они зависят от платформы. |
| Диагностика связывает этапы одним `op_id`, а секреты и сообщения не попадают в журнал через форматирование либо обёртку (ARCH-14). | Сверить путь данных на ревью и проверить журналы сценария на синтетических значениях. |

Граф показывает, какие ссылки найдены между участками кода и какие из них нарушают правило. Порядок действий, выбор ветки и владелец объекта в момент записи определяются при выполнении сценария.

Проверка `ARCH-08` узнаёт прямые пути по импортируемым именам из Cargo. Происхождение типа через фасад или реэкспорт из разрешённого файла, одноимённые локальные модули и код после раскрытия макросов требуют разрешения имён средствами компилятора. Условный `#[path]`, который нельзя определить однозначно при `test = false`, возвращает ошибку анализа с путём модуля.

## Результат пробы ArchUnitRust

- Синтетический проект подтвердил распознавание группового `use`, локального alias, прямого пути и `#[path]`. Интеграционный тест был исключён. Внутренний и вынесенный в отдельный файл `#[cfg(test)]` модули попали в рабочий граф и дали ложные ссылки на `rusqlite`.
- В цепочке реэкспорта граф указал на промежуточный файл. Этого недостаточно, чтобы отличить реэкспорт типа драйвера от допустимого типа, объявленного в `storage`.
- На рабочем дереве извлечение дошло до четырёх рабочих targets и вернуло 2 877 сообщений `unknown-reference`. Для первого правила достаточно проверить прямые синтаксические ссылки на драйвер в доступных рабочему коду файлах. Точное происхождение типов за фасадами и раскрытие макросов остаются за анализом компилятора. [Извлечение графа](https://github.com/dragonsec-ai/ArchUnitRust#rust-dependency-extraction)

## Приёмка инструмента перед включением проверки

1. Проверить выбранную версию на текущем дереве и небольших примерах. Для Cargo проверить обычную, переименованную, target-specific и тестовую зависимости. Для графа — групповой `use`, `use ... as`, `pub use`, прямой путь в типе или вызове, `crate`/`self`/`super` и `#[path]`. Файлы `history/` уже подключаются под `conversation` через `#[path]`. [Объявления модулей](../../../crates/workspace-desktop/src/gpui_client/conversation.rs)
2. Отдельно проверить `#[cfg(test)]` внутри рабочего target, тестовые targets и ветки macOS с `gpui`. Запуск из любой ОС должен проверять и ветки, которые нельзя выполнить на этой ОС.
3. Прогнать разрешённые примеры из таблицы и по одному нарушению для каждого правила. Проверить охват нужных исходников и targets. Ошибка чтения или разбора рабочего исходника должна завершить проверку с ошибкой. Диагностика нарушения должна назвать правило, источник, цель и, для исходников, файл и строку.
4. Включать в обязательный прогон только правила, для которых примеры проходят с ожидаемым результатом. Для новых границ сначала уточнять владельца и допустимые связи в архитектуре, затем добавлять проверку.

## План реализации и приёмки

| Этап | Ответственность и результат | Приёмка |
| --- | --- | --- |
| 1. Проверка ArchUnitRust | В изолированном каталоге проверить закреплённый `archunit` на синтетических примерах и текущем дереве. Параллельно можно реализовать правила Cargo. | Получить воспроизводимый ответ для каждой обязательной формы ссылки и для тестового исключения. Если версия недоступна или извлекает граф неполно, зафиксировать причину и использовать узкую проверку исходников через `syn`. |

Переименованный запрещённый пакет, в том числе под платформенным условием, и поломка headless-конфигурации дают диагностику с ID правила. |

Независимое ревью и проверка | Сверить точный набор правок, прогнать автотесты и общую команду на рабочем дереве и на синтетическом нарушении. | Проверить затронутые команды Cargo, отдельно отчитаться о сбоях существующих тестов и проверить, что изменения ограничены инструментом, его подключением и документацией. |

Тесты проверяют и допустимый код, и отказ на конкретном нарушении. На macOS отдельно проверяем headless CLI без default features и разрешённый граф его пакета для этой конфигурации. Результат проверки архитектуры применяется и к текущим незакоммиченным изменениям.

## Вызов из рабочего процесса

Человек, агент и CI запускают `cargo check-architecture` из корня checkout. Агент запускает проверку при изменении манифеста или Rust-кода, который затрагивает границу модулей, и передаёт результат вместе с итогом ревью. При подключении CI добавляем эту команду отдельным шагом с Rust stable. Сейчас в репозитории нет конфигурации CI. Закреплённые версии зависимостей берутся из lock-файла dev-инструмента. Команда не требует GUI, тестовых аккаунтов или запущенного сервиса.

При изменении самого инструмента отдельно запускаем его тесты. У него отдельный Cargo workspace. [Правила для агентов](../../../AGENTS.md#ревью) · [Проверка на ревью](../../../skills/workspace-desktop-review/SKILL.md#как-проверять)

```sh
cargo test --locked --manifest-path tools/workspace-architecture/Cargo.toml --target-dir target/architecture-lint
```

## Результат первого среза
