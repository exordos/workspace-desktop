# Кэш вложений мессенджера. План Core

[Каталог функций](../features/messenger/files.md#локальные-копии) · [Файловый контракт](../modules/messenger-files.md#чтение-и-скачивание) · [UI-15](ui-parity/ui-15.md)

Начинаем с вложений обычных сообщений в доступных личках, группах и темах. Первый результат без окна: Core открывает вложение через файловый API, сохраняет полную копию и при следующем открытии отдаёт её с диска без HTTP. Событие отзыва доступа сразу делает запись недоступной. Подготовленные к отправке файлы и копии, сохранённые пользователем через «Сохранить как…», имеют собственный жизненный цикл.

## Что хранить

У вложений один кэш для фото, видео, аудио и документов. Вид файла помогает фильтровать и выбирать политику хранения. Оригинал и будущие миниатюры или постеры используют отдельные варианты записи по ключу `OwnerContext + file_uuid + вариант`. На первом этапе нужен оригинал. Аватарки остаются в [кэше справочника](../features/foundation/directory.md#dir-005).

В существующей SQLite храним две связанные проекции:

- **Вложения из известной истории.** Действующая прямая ссылка, владелец, стрим, тема, UUID сообщения и файла, дата и вид. У файла может быть несколько размещений. Проекция обновляется при записи REST-страницы и при применении события истории. Правка или удаление сообщения меняет его связи. Существующая история индексируется при первом использовании в доступной области. Галерея получает страницы по дате и показывает вложения даже без локальной копии. В сведениях Core считает фото, видео, файлы и ссылки по той же области, с которой откроется галерея. Полнота ограничена известной клиенту историей.
- **Локальные копии.** Ключ варианта, служебный путь, размер, время последнего использования и доступные метаданные, включая известный `stream_uuid` файла. Байты лежат отдельными файлами в каталоге кэша профиля. Один вариант занимает место один раз в пределах владельца. Core открывает копию под действующим поколением сессии и возвращает управляемое чтение. Сырой путь к кэшу остаётся внутри его реализации.

`core::messenger` владеет выбором источника, доступом, загрузкой и командами управления. `core::storage` владеет индексами, транзакциями и учётом байтов. `core::sync` доставляет события. Путь к каталогу передаёт собирающий приложение код, Core использует его и в проверках с временным профилем. [Изоляция записей](../modules/storage.md#изоляция-аккаунтов) · [Применение событий](../modules/runtime.md#как-событие-доходит-до-sync)

## Операции Core

| Операция | Результат |
| --- | --- |
| Открыть вложение | При известном доступе, действующей сессии и прямой ссылке в доступном сообщении выдать готовый вариант локально. При промахе запросить оригинал напрямую из файлового API, где сервер проверит права. Одновременные запросы одной сессии к одному варианту используют одну передачу. |
| Список вложений стрима или темы | Постранично вернуть ссылки из доступной известной истории с датой, видом и признаком наличия копии. Обновление истории и очистка байтов независимы. |
| Список копий и расчёт места | Постранично вернуть сохранённые варианты по аккаунту с фильтрами по стриму, теме и виду, сортировкой по размеру или последнему использованию. Сводка опирается на индекс и считает физический размер каждой копии один раз. |
| Очистить кэш | Очистить выбранный вариант или файл, набор файлов, стрим или тему, тип либо весь кэш вложений выбранного владельца. Вернуть оценку до операции и результат после неё, включая реально освобождённые байты и копии, которые ещё ожидают удаления. |
| Вытеснить по бюджету | После успешной записи и при восстановлении профиля сверить занятое место с бюджетом. При превышении сначала вытеснить давно не использовавшиеся копии. Предельный размер одного объекта ограничивает расход на большие файлы. |

При очистке темы или стрима общая копия остаётся, если индекс знает о действующей ссылке вне выбранной области. Результат показывает, что место за неё сохранилось. Явный выбор файла или полный сброс кэша владельца освобождает байты независимо от числа таких ссылок. Сообщения и связи из истории доступны для повторной загрузки с учётом прав. Очистка использует актуальный набор записей и сообщает итог по состоянию на момент выполнения. [Проверки очистки](#приёмка-core)

## Порядок реализации

### 1. Локальный индекс и готовая копия

Добавить таблицы и индексы через штатный `Storage::open`. Переиспользовать общий разбор Workspace-ссылок из UI-14/15 и `HistoryScope`. Привязать индексацию к `Storage::save_history_page` и `Storage::apply`, обновлять связи сообщения в той же транзакции. Для сохранённой истории переиспользовать те же правила при первой индексации выбранной области. Проверить дубликаты ссылок, смену темы, изоляцию владельцев и повторное открытие профиля.

### 2. Доступ и передача оригинала

В файловом модуле `MessengerSource` переиспользовать подтверждение разговора, полученное при штатном открытии истории. При попадании Core проверяет доступ локально. При промахе сервис читает `GET /files/{uuid}/actions/download` порциями с токеном исходной сессии. Метаданные берём из доступного контекста и ответа API, а отдельный запрос используем, если метаданные нужны вызывающему коду. Без сведений о файловом стриме копия доступна в стримах, для которых уже был успешный запрос её байтов. Первый доступ из другого стрима проходит через файловый API. Успешный запрос добавляет подтверждённый стрим к той же копии.

Одна работа на `(владелец, поколение, файл, вариант)`. Участники получают свой результат после проверки применимости их исходной ссылки. Пишем в отдельный временный файл, проверяем фактическую длину, лимит и доступные данные целостности. После завершения атомарно перемещаем байты на том же томе и публикуем запись в индексе. Временный файл удаляется при отмене, обрыве или сбое записи. При запуске запись без файла считается промахом, а оставшиеся после сбоя временные или бесхозные файлы убираются. `Storage` и сессию блокируем только на коротких проверках и фиксации.

### 3. Отзыв и гонки

Сделать этот этап частью первого проверяемого среза. Переиспользовать принятые в Core события правки, удаления, потери темы или стрима, `file.deleted` и сброса источника. Проверить контракт `file.updated` перед тем, как использовать его для обновления файла. Событие потери стрима убирает затронутые связи. Отзыв по известному стриму самого файла затрагивает все варианты такого файла в контексте владельца. При неизвестном файловом стриме отзыв одного из стримов, через которые скачивали копию, блокирует её выдачу до нового успешного запроса файла. Отказ файлового API `403/404` и удаление файла инвалидируют варианты соответствующего UUID. Правка или удаление сообщения прекращают выдачу через эту ссылку.

Фиксировать инвалидирование в одной транзакции с изменением истории и курсора, байты удалять после фиксации с возможностью повтора. Каждая запись новой копии получает свой служебный путь, поэтому повтор удаления старой версии сохраняет свежую копию того же ключа. При очистке и отзыве отменять затронутые передачи. Перед публикацией проверять поколение сессии и актуальность записи, области и исходной ссылки. Запоздалый ответ не возвращает очищенную копию. При сбросе источника закрывать доступ до получения актуальной истории. Смена активного аккаунта меняет контекст потребителя, выход отзывает поколение. [Сброс и события](../modules/sync.md#восстановление-и-проверка)

### 4. Управление размером

Добавить выборки с курсором, оценку места, команды очистки и итог операции. Проверить подсчёт общих копий и сбой удаления на диске. Подключить бюджет и вытеснение. В Core стартовые значения составляют 512 МиБ на профиль и 64 МиБ на один оригинал. Пределы передаются при открытии кэша. При превышении бюджета Core вытесняет копии по давности последнего чтения. Проверки используют заданные малые лимиты. Возраст автоочистки и пользовательские настройки бюджета остаются продуктовыми решениями.

## Приёмка Core

- **Штатный вход и два аккаунта.** Открыть подтверждённую историю, скачать вложение и открыть его снова после перезапуска профиля. Локальное попадание не делает HTTP при уже подтверждённом доступе. Одновременные промахи делают один GET. Аккаунт B не читает копию A по тому же UUID. Счётчик запросов ведётся после открытия истории.
- **Гонки и отзыв.** На локальном HTTPS/WS задержать ответ, затем очистить вариант, удалить файл или отозвать доступ к стриму. Старый ответ не публикуется, доступ к уже открытой копии прекращается. Отдельно проверить `403/404`, повторный вход того же аккаунта и сброс курсора. Переиспользовать окружение [`direct_history.rs`](../../../crates/workspace-core/tests/support/direct_history.rs) и [`catalog_revocation.rs`](../../../crates/workspace-core/tests/support/catalog_revocation.rs).
- **Диск и целостность.** На временном профиле проверить неполную передачу, отказ записи, состояние после перемещения файла до записи индекса и запись без файла. Каждая неполная копия недоступна и исчезает при восстановлении. Активное чтение и неудачное удаление не увеличивают число освобождённых байтов до фактической очистки.
- **Очистка и бюджет.** Один файл в двух темах учитывается один раз в общей сводке. Очистка одной темы сохраняет общую копию для второй, явная очистка файла освобождает место один раз. Повтор удаления старой версии после новой загрузки сохраняет свежую копию. Выборка известной истории продолжает возвращать сообщения. Вытеснение соблюдает лимит и изоляцию контекстов.

Этапы 1–3 готовы, когда этот путь проходит через штатные входы Core во временном профиле и локальном HTTPS/WS. После этапа 4 Core готов для подключения списка и очистки в интерфейсе. Диагностика связывает открытие, запись, очистку и отказ по `op_id`, использует статусы и объёмы. [Правила журналов](../workspace-desktop-architecture.md#диагностические-журналы) · [Проверки проекта](../../../AGENTS.md#проверки-из-корня-workspace)

### Результат первого прогона

Кэш подключён к профилю окна и команде синхронизации без окна. Приёмка Core во временном профиле и на локальном HTTPS/WS подтвердила чтение с диска, объединение загрузок, изоляцию аккаунтов, очистку общих копий и отсечение старых ответов после отзыва. Доступность серверных превью и поведение на развёрнутом стенде требуют отдельной проверки. Сценарии GPUI остаются на этапе UI-15.

## Следующие этапы

Галерея и экран настроек подключаются поверх команд Core. Серверные миниатюры и постеры видео добавляются после появления API как новые варианты, с теми же проверками контекста. Полная галерея за пределами полученной истории зависит от серверной выдачи вложений по сообщениям. Потоковое воспроизведение и перемотка требуют отдельного контракта `Range` и `206`. Офлайн-закрепление и E2EE требуют собственных правил доступа и хранения. [Серверные превью](../modules/messenger-files.md#серверные-превью)
