Срез от 27 ноября 2026 года. Базовые API появились в backend `3.4.0`, подключение IMAP/SMTP и CalDAV — в `3.4.1`. Ниже использован контракт из тега `3.4.2`. [Релиз 3.4.0](https://github.com/exordos/workspace_backend/releases/tag/3.4.0) · [Релиз 3.4.1](https://github.com/exordos/workspace_backend/releases/tag/3.4.1) · [OpenAPI](https://github.com/exordos/workspace_backend/blob/3.4.2/docs/public_workspace_api.yaml)

С токеном тестового IAM-проекта запросы списков внешних аккаунтов, папок, писем, черновиков, календарей и событий вернули `200`. Проверка охватывала чтение коллекций. В отчёте бэкенда отдельно подтверждены доставка по SMTP, импорт по IMAP и создание, изменение и удаление события через CalDAV. [Проверки бэкенда](https://github.com/exordos/workspace_backend/pull/340)

## Общий вход и синхронизация

Все пути ниже указаны относительно `/api/workspace/v1`. Запросы используют Bearer-токен выбранного IAM-проекта. Почтовые и календарные объекты принадлежат текущему пользователю в этом проекте. Внешний аккаунт — подключённый ящик или календарный сервис внутри этого контекста. У пользователя может быть несколько подключений. [Общий контракт](https://github.com/exordos/workspace_backend/blob/3.4.2/docs/en/workspace_api.md)

| Сценарий | Возможность API и условия |
| --- | --- |
| Список подключений | `GET /external_accounts/`, один аккаунт по UUID. Поля `provider` и `capabilities` помогают выбрать подключения для нужного раздела. |
| Подключение | `POST /external_accounts/`. Для `imap_smtp` передаются email, IMAP- и SMTP-адреса с настройками TLS и пароль. Почтовые серверы должны быть доступны по публичным IP и предъявлять доверенный сертификат. Для `caldav` передаются HTTPS-адрес, имя пользователя и пароль. Пароль хранится на сервере в зашифрованном виде и скрыт в ответах и событиях. |
| Статус и переподключение | `GET` и `PUT /external_accounts/{uuid}`. API сообщает `status`, `error_description` и `disabled`. Отключение через `disabled: true` сохраняет импортированные данные. Отправки в очереди блокируют отключение ящика. Для повторного включения нужен новый запрос с паролем. Удаление через `DELETE /external_accounts/{uuid}` доступно для аккаунта без связанных папок и календарей. |
| Обновления | Общие `GET /events/` и `/events/ws` с курсором `epoch_generation`, `epoch_version`. События `external_account.*`, `mail.folder.*`, `mail.message.*`, `mail.draft.*`, `calendar.calendar.*` и `calendar.event.*`. При истечении курсора общий протокол предусматривает повторное чтение снимков. |

[Контракт внешних аккаунтов и CalDAV](https://github.com/exordos/workspace_backend/blob/3.4.2/docs/en/calendar_api.md#external-accounts) · [Типы событий](https://github.com/exordos/workspace_backend/blob/3.4.2/workspace/messenger_api/dm/event_payloads.py)

## Почта

| Сценарий | Возможность API и условия |
| --- | --- |
| Папки и непрочитанное · [MAIL-005](../features/sections/mail.md#mail-005) | `GET /mail/folders/` возвращает тип папки, привязку к ящику и `unread_count`. Папку можно создать и переименовать. Удаляется пустая папка. IMAP импортирует папки, письма и вложения, пропуская письма больше 16 МиБ в исходном виде. |
| Список и открытие письма · [MAIL-005](../features/sections/mail.md#mail-005) | `GET /mail/messages/` с пагинацией и фильтрами, в том числе по папке и внешнему аккаунту. `GET /mail/messages/{uuid}` возвращает адреса, тему, тело `multipart` с текстом и HTML, ссылки на вложения и флаги. |
| Черновик и ответ · [MAIL-006](../features/sections/mail.md#mail-006) | Список, создание, чтение, обновление и удаление через `/mail/drafts/`. Есть `to_addresses`, `cc_addresses`, `bcc_addresses`, тема, текст или HTML. `reply_to_uuid` связывает ответ в Workspace. SMTP-код `3.4.2` не переносит связь в заголовки внешнего письма. |
| Отправка · [MAIL-006](../features/sections/mail.md#mail-006) | `POST /mail/drafts/{uuid}/actions/send/invoke` ставит отправку в очередь и создаёт письмо с UUID черновика. SMTP подключённого ящика обрабатывает очередь. Итог сверяется по письму и `delivery_status` (`queued`, `sent`, `failed`). |
| Вложения · [MAIL-007](../features/sections/mail.md#mail-007) | Загрузка через `POST /messenger/files/` с ACL владельца. Письмо и черновик ссылаются на файлы через `attachment_urns` (`urn:file:<uuid>`). Байты читаются через `GET /messenger/files/{uuid}/actions/download` с проверкой доступа. |
| Действия над письмом · [MAIL-008](../features/sections/mail.md#mail-008) | `read`, `unread`, `star`, `unstar`, `move`, `trash`, `restore` через `/mail/messages/{uuid}/actions/{name}/invoke`. Перемещение внутри одного ящика. В том числе можно выбрать папку типа `archive`. Удаление доступно через `DELETE /mail/messages/{uuid}`. Действия над импортированным письмом меняют копию в Workspace. |
| Фон и счётчик · [MAIL-009](../features/sections/mail.md#mail-009) · [MAIL-010](../features/sections/mail.md#mail-010) | События почты и серверный `unread_count` по папке дают данные для списка и сводки. Правила системных уведомлений и открытия исходного письма определяет Desktop. |

Для сверки с макетами отметить полнотекстовый поиск, цепочки, пересылку, массовые операции и детали ошибок SMTP. В контракте есть фильтры по полям, ответ по `reply_to_uuid`, одиночные операции и статус отправки. Отдельных API для перечисленных сценариев не найдено. [Контракт почты](https://github.com/exordos/workspace_backend/blob/3.4.2/docs/en/mail_api.md) · [Спецификация списка писем](https://github.com/exordos/workspace_backend/blob/3.4.2/docs/public_workspace_api.yaml#L7858)

## Календарь

| Сценарий | Возможность API и условия |
| --- | --- |
| Список календарей · [CAL-005](../features/sections/calendar.md#cal-005) | `GET /calendar/calendars/` и чтение по UUID. Доступны имя, связь с внешним аккаунтом, `primary` и `read_only`. Личный календарь можно создать, переименовать и удалить, когда он пуст. Списком календарей CalDAV управляет провайдер. |
| Расписание и карточка · [CAL-005](../features/sections/calendar.md#cal-005) | `GET /calendar/events/` с пагинацией и фильтром `calendar_uuid`. Для пересечения с видимым периодом передаются исключительные границы `starts_before` (конец периода) и `ends_after` (начало). `GET /calendar/events/{uuid}` возвращает название, описание, место и время начала и конца в UTC. |
| Создание, редактирование и удаление · [CAL-006](../features/sections/calendar.md#cal-006) | `POST /calendar/events/`, `PUT` и `DELETE /calendar/events/{uuid}`. Поддерживаются разовые события в личных календарях и календарях CalDAV с правом записи. С CalDAV запись учитывает ETag провайдера. Для повтора создания CalDAV после потери ответа можно использовать тот же клиентский UUID и те же данные. |
| Перенос в другой календарь · [CAL-006](../features/sections/calendar.md#cal-006) | `POST /calendar/events/{uuid}/actions/move/invoke` с `calendar_uuid`. Перенос между личными календарями, доступными для записи. |
| Фоновое обновление · [CAL-009](../features/sections/calendar.md#cal-009) | Работает через общие события Workspace. CalDAV импортирует разовые события в пределах года в обе стороны от текущей даты. |

Для сверки с макетами отметить повторения, участников и ответы на приглашения, напоминания, перенос между CalDAV-календарями и отдельный признак «весь день». У события есть пара UTC-меток, по которой клиент строит отображение. Для сохранения семантики «весь день» и исходного часового пояса понадобится уточнение контракта, если этого требуют макеты. [Контракт календаря](https://github.com/exordos/workspace_backend/blob/3.4.2/docs/en/calendar_api.md) · [Модель события](https://github.com/exordos/workspace_backend/blob/3.4.2/workspace/calendar_api/models.py)

## Подключение к Desktop

В Desktop уже есть навигация «Почта» и «Календарь». Сейчас оба входа открывают заголовки разделов. В Core общими являются сессия IAM, контекст владельца и выбор сетевого маршрута. Текущий REST-клиент закрыт внутри Messenger и связан с его запросами, типами и ошибками. В выдаче доступа по сервисам пока реализован Messenger. Запросы к почте и календарю на стенде прошли с тем же типом токена IAM-проекта. [Текущий экран](../../../crates/workspace-desktop/src/gpui_client/client.rs#L1252) · [REST-клиент Messenger](../../../crates/workspace-core/src/messenger/rest.rs#L66) · [Выбор маршрута](../../../crates/workspace-core/src/workspace_direct.rs)

Предлагаемые границы для первого среза:

- Почта и календарь в Core владеют своими запросами, форматом ответов и типизированными операциями. Для первого сценария зафиксировать, как адаптер получает токен текущего проекта, форму списка и карточки, пагинацию, обработку отказов и сброс позднего ответа после выхода из аккаунта.
- Оболочка ведёт выбранный аккаунт и экран. GPUI вызывает операции Core. Поля OpenAPI, токены и правила синхронизации остаются внутри Core.
- При появлении второго адаптера проверить фактическое дублирование в сборке HTTPS-запроса, авторизации и чтении страниц. Общий код для файлов и журнала событий рассмотреть при подключении этих операций. [Контракт разделов](../modules/sections.md) · [Файловый API в Desktop](../modules/messenger-files.md#чтение-и-скачивание)

## Следующая итерация

1. Выписать из макетов действия и состояния каждого экрана. Для каждого указать ID из каталога, соответствующую строку этого плана и условия API.
2. Отметить, какие сценарии целиком обеспечены API, какие требуют решения на клиенте и для каких нужен ответ или изменение бэкенда.
3. По результату выбрать первый срез и описать его вызов от входа в раздел до результата, включая границы адаптера и форму данных для экрана. Кандидаты из дорожной карты — «список папок → письмо» и «календарь → период → событие».
4. При реализации проверить нужные операции на тестовых данных и переключение между аккаунтами. Для записи отдельно проверить итог в сервисе и поведение после потери ответа.
