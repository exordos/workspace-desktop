## Поведение

В личке или открытой теме пользователь видит карточку вложения в истории. Она показывает имя, размер и состояние получения. У изображения есть превью. Клик открывает просмотр с закрытием по Escape и возвратом фокуса к источнику. Если в загруженной истории несколько изображений, видны переходы, миниатюры и масштаб. Отказ получить файл оставляет сообщение видимым и показывает причину и доступное действие.

Лёгкие серверные миниатюры фото и постеры видео откладываем до появления API. В первом срезе для фото используется локальное превью в пределах лимита чтения. Для видео показываем карточку с заглушкой и загружаем оригинал по действию пользователя. [Подключение серверных превью](../../modules/messenger-files.md#серверные-превью)

Кнопка прикрепления, перетаскивание и вставка принимают файл или изображение. После проверки начинается загрузка с прогрессом и действиями «Отменить», «Повторить» и «Убрать». Готовое вложение можно отправить без текста. Нажатие на скачивание предлагает безопасное имя и место, показывает прогресс и итог. Для завершённой записи доступны «Открыть» и «Показать в папке».

## Что есть в штатном клиенте

- `src/bin/workspace-desktop.rs` → `gpui_client::run` → `RuntimeClient` и `Client` → открытие `Conversation` по `ConversationAddress`. Адрес включает `OwnerContext`, точную область истории, поколение входа и ревизию перехода. Команды, привязанные к экрану, могут переиспользовать `RuntimeClient::conversation` и `ConversationReply::for_current`.
- `conversation.rs` → `history/source.rs` → `MessengerSource` → подтверждение доступа и страницы истории → `Storage` → `history/viewport.rs`. REST и события сохраняют исходный Markdown. `Viewport::build_rows` выделяет прямые ссылки на вложения подтверждённых сообщений и передаёт карточки в `history/attachments.rs`. Оригинал фото открывается через [дисковый кэш Core](../messenger-media-cache.md) с допуском текущей истории.
- `composer.rs::submit` → `Conversation::save_submission` → `composer/source.rs::SendSource` → `Sync::prepare_send` → SQLite `PreparedSend.markdown` и очередь → `MessengerSource::post_prepared_message`. Снимок отправки неизменен и хранит готовое тело. Проверки маршрута, поколения и допуска обычного Markdown повторяются перед первым POST. Они уже есть и подходят для сообщения, в которое добавлены подтверждённые ссылки.
- `SyncChange::MediaFileInvalidated` снимает просмотр и превью изменённого или удалённого файла. Обновление сообщения, отзыв доступа или смена разговора также снимают показ и отменяют ожидание результата.

Пути `gpui_client/…` ниже отсчитываются от `crates/workspace-desktop/src`, `messenger/…` — от `crates/workspace-core/src`.

## Серверный контракт

Проверен код `workspace_backend@bc986e07981737f57eeb5b205a5bee25c42e8858` и его утверждения тестов. Один multipart `POST /api/workspace/v1/messenger/files/` передаёт `file`, `stream_uuid`, опционально `name` и `description`. В личке и теме используется потоковый ACL `stream_members`. Широкий ACL `public` существует у сервера для других сценариев. `WorkspaceFileController._create_from_multipart` создаёт UUID внутри запроса и возвращает запись с UUID, потоком, владельцем, именем, MIME, размером и SHA-256. Идемпотентный ключ upload в обработчике отсутствует. Потеря ответа, обрыв, отмена и 5xx после отправки байтов могут оставить созданный файл, UUID которого клиент не знает. Ссылки на источники — [API файлов](https://github.com/exordos/workspace_backend/blob/bc986e07981737f57eeb5b205a5bee25c42e8858/docs/en/workspace_api.md#files) и [контроллер](https://github.com/exordos/workspace_backend/blob/bc986e07981737f57eeb5b205a5bee25c42e8858/workspace/messenger_api/api/controllers.py#L460-L675).

`GET files/{uuid}` возвращает разрешённые метаданные, `GET files/{uuid}/actions/download` — авторизованные неизменяемые байты. Сервер проверяет видимость в текущем проекте и составе потока. Ответ имеет MIME, `Content-Disposition`, `ETag` и `Cache-Control: private, no-cache`. `DELETE files/{uuid}` доступен владельцу файла. В тестах доступ исчезает при отзыве членства и не переносится между проектами. Доступ может скрываться за 404. Формулировка «Файл недоступен» сохраняет смысл и при удалении, и при запрете. Источник — [тесты ACL](https://github.com/exordos/workspace_backend/blob/bc986e07981737f57eeb5b205a5bee25c42e8858/workspace/tests/integration/test_workspace_file_authority.py).

Сообщение хранит обычный Markdown. Сервер документирует `[имя](urn:file:<UUID>?name=...)`, `![имя](urn:image:<UUID>?name=...)` и `urn:video:<UUID>`. Идентификатор берём из проверенного URN, имя для сохранения — из авторизованных метаданных; параметры URN служат подсказкой для отображения. URL запроса формирует `core` из HTTPS-адреса владельца, фиксированного пути и проверенного UUID. Строка из сообщения, имя файла и заголовки ответа не задают сетевой адрес или системный путь. Для локальных размеров и прав при скачивании сервер остаётся источником истины. Источник — [формат сообщений](https://github.com/exordos/workspace_backend/blob/bc986e07981737f57eeb5b205a5bee25c42e8858/docs/en/workspace_api.md#messages).

Серверный документ указывает предел 50 MiB на весь multipart-запрос у ingress. До включения загрузки сверить лимит целевого развертывания и выбрать локальное ограничение для файла с учётом длины multipart. Распознавать 413 отдельно, в том числе при расхождении лимитов. Тест ACL утверждает 201 при загрузке PNG. Общий тест multipart допускает 200/201, сверяет Unicode-имя, MIME, байты и SHA-256. Закрепить поддерживаемые ответы в loopback. Допустимые форматы и нулевой размер для предварительной проверки сверить с референсом и целевым API. Для Zulip совместимость чтения основывается на тех же Workspace URN. Гарантии загрузки и доставки через провайдера требуют отдельного прогона.

Серверные `file.updated/deleted` и `stream.deleted` влияют на состояние превью. Удаление пользователя из потока даёт ему `stream.deleted`; разрыв эпохи требует очистки производных защищённых данных. Тема нужна для проверки источника сообщения, серверный файловый ACL ограничен потоком. Источник — [realtime API](https://github.com/exordos/workspace_backend/blob/bc986e07981737f57eeb5b205a5bee25c42e8858/docs/en/workspace_ui_realtime_integration.md).

## Ответственность и инварианты

- `core::messenger` владеет синтаксисом Workspace-ссылок, доступом, HTTP, состояниями передачи и сроком жизни разрешённых данных. Минимальный тип операции включает владельца, поколение, область, UUID исходного сообщения и UUID файла. Для открытия готовой копии Core локально сверяет действующий вход, известный доступ к разговору и ссылку в истории. При передаче байтов с сервера права проверяет файловый API в самом запросе. Перед выдачей результата проверяем поколение, UUID и актуальность операции. [Правила чтения и отзыва](../../modules/messenger-files.md#чтение-и-скачивание)
- `desktop::gpui_client::conversation` владеет привязкой ответа к текущему окну, ревизии, строке и попытке. Выбор аккаунта, переход A → B → A на тот же UUID, закрытие просмотра, исчезновение/изменение исходного сообщения, отзыв маршрута и выход должны сбрасывать соответствующие запросы и отображение. Для первого среза держим превью только в памяти открытого разговора с лимитом по байтам/изображениям. Срок жизни декодированного изображения связан с тем же разрешением; переиспользование средствами GPUI допускается только с очисткой при отзыве. Для результата завершения нужны и проверка перед применением, и отмена выполняющейся операции.
- `desktop::platform` отвечает за выбор файлов и пути, локальную запись, открытие и показ в Finder. GPUI 0.2.2 уже предоставляет `App::prompt_for_paths` и `App::prompt_for_new_path`, а также данные изображений clipboard. Для сетевого потока и временной локальной копии использовать существующий рабочий поток и отдельно проверить отмену передачи при завершении. Доступ к сохранённому пользователем файлу определяется ОС. Отзыв удаляет защищённые превью и незаконченные копии приложения, сохранённая пользователем копия остаётся по [MSG-E2EE-007](../../features/messenger/encryption.md#msg-e2ee-007).
- Начальный сценарий — подтверждённый обычный Markdown. `WireHistoryMessage` сейчас фильтрует остальные типы, а отправка блокирует шифрованный или неизвестный режим. Для [MSG-FILE-010](../../features/messenger/files.md#msg-file-010) отдельной зависимостью остаются E2EE и защита ссылок при расшифровке: исходно зашифрованные ссылки появляются только в памяти после проверки ключа, байты файлов защищает серверный ACL. Отзыв ключа прерывает превью и очищает производное состояние. Обычный загрузчик открывает файлы только по проверенной открытой ссылке сообщения. Вложения в защищённом редакторе надо подключать вместе с безопасной подготовкой шифротекста.
- `op_id`, операция, стадия, объём/статус, категория ошибки и разрешённый контекст нужны для диагностики. Не логировать байты, пути, имя пользователя/файла, запрос или ссылку, распознанный кусок Markdown или ответ целиком. Для проверки прокрутки сохранить UUID опоры, координаты до/после и поправку.

### 1. Ссылка, карточка и превью — MSG-FILE-006 и очистка MSG-FILE-011

1. Утвердить единый разбор entity-ссылок Markdown с UI-14. На входе стандартная ссылка/картинка и корректный UUID, на выходе типизированная ссылка с диапазоном в исходном тексте. Цитата или snapshot пересылки сами по себе не дают новый доступ к вложению. Ограничить разбор ссылок поддерживаемым Markdown-контекстом. Проверить библиотеку Markdown при выборе подхода и закрепить зависимость одним владельцем, если текущих средств недостаточно. До согласования можно независимо начать узкий сетевой модуль и его тесты.
2. В `messenger/files.rs` добавить авторизованные метаданные и чтение с лимитом. Использовать те же проверку `workspace_origin`, TLS/private CA и запрет redirect, что у `RestClient`. Для вложения использовать сведения о доступе, которые уже получил мессенджер, и локально сверять область сообщения. Ошибки доступа, сети и невалидного ответа становятся явными типами.
3. В `gpui_client/history/attachments.rs` проецировать проверки и состояние карточек. В `history/viewport.rs` собирать блоки строки один раз при замене снимка, оставляя текстовые строки, группировку, timestamp и public ID без изменений. `ui/content.rs` меняется только при реальной необходимости поддержать новый слот в пузыре. Карточка использует текущие `ui/theme.rs`, `ui/icons.rs` и кнопки. Список имеет ограниченный запрос для видимых вложений. Декодирование растровых изображений вне потока окна, с ограничениями на объём, число пикселей и с проверкой формата. SVG/HTML/исполняемое содержимое отображается как обычный файл. До готовности размеров и в ошибке сохраняем габарит placeholder либо используем существующий путь сохранения `Viewport`-опоры при переносе строки.
4. События удаления/правки сообщения, потери потока и темы, недоступности аккаунта и отставания подписки сбрасывают состояние источника и скрывают превью. Для целевой точности подключить инвалидирование UUID по проверенным `file.updated/deleted` через `messenger/rest.rs`, `sync.rs` и обработку `Conversation::apply_sync`; привязать к владельцу, поколению и принятому порядку событий. На 403/404 очистить связанные метаданные/байты и показать отказ. При повреждённом превью скачивание файла остаётся доступно, если сервер подтверждает доступ.
5. **Приёмка.** Core/loopback: готовая копия в доступном разговоре открывается без HTTP. При отсутствии копии запрос файла идёт токеном A к A без повторного запроса сообщения или членства. Неизвестная или чужая ссылка не запрашивается, 403/404/redirect дают отказ, после переавторизации поздний результат не применяется, размер и MIME-ошибка стабильны, событие файла/отзыв/смена эпохи убирают данные. GPUI: реальная строка через `Conversation` показывает текст, карточку, загрузку, ошибку и валидное превью; A → B → A не возвращает поздний preview. Позднее изображение воспроизвести с несколькими размерами и измерить эту же опорную строку на 600 сообщениях, положение у хвоста и отсутствие прыжка при отказе. UI-11 предоставляет `history/stability.rs` и диагностику.

### 2. Скачивание — MSG-FILE-008 и MSG-FILE-009

1. Для `prompt_for_new_path` использовать доступные метаданные и при необходимости запросить их для имени файла. Зафиксировать контекст действия. После выбора места отправить запрос скачивания, в котором сервер проверит права. При отмене диалога или новом переходе до выбора передача не начинается. Начатая передача привязана к исходному входу и доступу, принадлежность в списке загрузок фиксирована. Список не смешивает аккаунты. Выход, отзыв доступа и отмена задачи очищают незаконченную копию.
2. Переиспользовать доступ из `messenger/files.rs`, передавать байты порциями с прогрессом (известный объём или неопределённый), лимитом, проверкой результата и идентичности попытки. В `platform/downloads.rs` хранить незаконченный файл рядом с целевым каталогом, завершать атомарно после полного потока и проверок. Применить поддерживаемое API атомарной записи без перезаписи для свободного имени. Подтверждённую пользователем замену обрабатывать отдельной веткой с проверкой, что целевой файл не изменился пока шла загрузка. Открывать и показывать в Finder по собственному завершённому `DownloadId`; убрать запись из списка оставляет пользовательский файл на диске. Пользовательские статусы и команды — в `gpui_client/conversation/downloads.rs`, платформенная интеграция использует существующий `NSWorkspace`.
3. **Приёмка.** Временный каталог: одинаковые имена двух операций, имя с разделителями или control-символами, отмена во время чтения и сразу перед фиксацией, недоступная папка, отказ сервера, разрыв потока и исходный файл на месте после отказа замены. Loopback: 401/403/404, неизвестная длина, достижение лимита, запрет redirect и смена входа в середине потока. GPUI: отмена/повтор, редактор другого чата сохраняет фокус. В нативном прогоне проверить выбор места, успешное открытие и показ в Finder синтетической текстовой копии, отмену диалогов и минимум окна. Отдельный общий экран загрузок с хранением журнала после рестарта выходит из первого среза и требует продуктового решения.

### 3. Просмотр изображений — MSG-FILE-007

1. В `gpui_client/history/media_viewer.rs` сделать просмотрщик с состояниями открытия, загрузки, изображения, ошибки и закрытия. Держать ссылку на клавиатурный якорь и на UUID сообщения и вложения. Навигация по валидным изображениям в текущем загруженном окне, стрелки ограничены границами, миниатюры используют тот же source. Изменение масштаба остаётся внутри просмотрщика. Прогресс и скачивание используют шаг 2. Продолжение галереи за пределами загруженной истории и видео имеют отдельные условия приёмки и не требуются для сценария фото UI-15.
2. В `conversation.rs` разместить оверлей поверх разговора без пересоздания истории. Escape закрывает просмотр до обработки команд оболочки, возвращает прежний видимый контроль. Если виртуальная строка исчезла, фокус идёт в историю текущего разговора. При отзыве доступа и переходе фокус выбирает новый экран по штатному пути. Догрузку, пока просмотр открыт, применять по UI-11, с сохранением UUID и координаты.
3. **Приёмка.** GPUI: открыть реальную карточку, быстро перелистнуть два элемента с обратным порядком ответа, проверить непустое изображение, навигацию, зум, Escape, фокус, прежнюю позицию и отказ. При закрытии, исчезновении исходной строки или переходе B → A поздний результат не открывает оверлей. Нативный сценарий проверить на 700 × 600 и 1440 × 900 в одном окне.

### 4. Добавление, загрузка и отправка — MSG-FILE-001…004

1. В `gpui_client/composer/attachments.rs` держать отдельный список с `local_id`, номером попытки, адресом, прогрессом и итогом. Подключить диалог к кнопке, затем drop и clipboard через `composer.rs` и, где нужно, `composer/editor.rs`. Обычная вставка текста и IME используют прежний путь. Отдельно проверить inline-вставку изображения в конкретное место текста и обычное вложение. Повторить проверки допустимости в `core`. Читать только явно выбранные обычные файлы, фиксировать размер снимка и обнаруживать его изменение. Изображение из буфера получает такой же лимит и валидацию.
2. `messenger/files.rs` добавляет stream multipart и разрешение назначения. Для загрузки до первого байта проверяем тот же допуск лички или конкретной темы и обычного текста, что при отправке. Использовать клиент без автоматического повтора мутации. В типизированной готовой ссылке сохранять проверенный UUID/stream/owner и попытку, имя очищается при форматировании Markdown. Прогресс привязан к переданным байтам и bounded concurrency. При явном отказе пользователь может повторить этот файл, остальные задачи продолжаются. Отмена прерывает локальную передачу. Если результат неизвестен, показать этот статус и возможность убрать запись. Автоматического POST нет. Повтор неизвестной операции отдельным действием возможен после решения о гарантиях и сценарии сирот.
3. «Отправить» доступно при готовом назначении и тексте либо готовом файле, пока все выбранные вложения готовы. Снимок `Submission` включает зафиксированный набор ссылок и ревизию редактора. `SendSource` передаёт намерение `core`, где готовые ссылки проверяются для этого scope и форматируются в Markdown по действующему контракту. Готовые ссылки попадают в существующий `PreparedSend.markdown` перед записью. Текст и файлы очищаются после фиксации, только если соответствуют отправленному снимку. Ошибка записи оставляет данные для повтора. Подтверждённое сообщение и исходящая строка показывают один и тот же набор вложений. Никакого второго upload при повторе сообщения.
4. Удалять серверный файл только если клиент может доказать, что сам загрузил его для этой попытки и ещё не зафиксировал ни в outbox, ни в сообщении или серверном черновике. Доказательство и отмена не должны проигрывать гонку с записью очереди. Для первой поставки согласовать судьбу известного неиспользованного файла, закрытия приложения после успешной загрузки и неизвестного UUID. До согласования правил владения не включать автоматический DELETE. Файлы с диска пользователя остаются по исходным путям.
5. **Приёмка.** Core: допустимость, 413, существующий токен исходного входа и stream UUID, cancel → late 201, неизвестный результат и отсутствие второго POST, retry одного файла, смена A → B → A. GPUI: выбор файла, прогресс и отмена, у вложения понятная ошибка, повтор, отправка без текста, ошибка SQLite, сохранение нового ввода и каретки при позднем завершении. HTTPS/WSS по примеру `gpui_client/client/loopback.rs`: получить один UUID upload, отправить один Markdown POST в явную тему, проверить один публичный UUID сообщения и те же ссылки в истории/локальной очереди. Закрытая тема, шифрование, смена поколения или API-отказ дают ноль POST там, где запись ещё не началась. Перезапуск после фиксации очереди подтверждает тот же Markdown без повторной загрузки.

### 5. Редактирование и зависимые функции — MSG-FILE-005 и MSG-FILE-010

- UI-14 определяет PUT, права и конфликты текста. В нём нужно сохранять точные исходные диапазоны уже имеющихся file URN, даже когда интерфейс правки файлов ещё не готов. Добавление/удаление из правки пользуется общим валидатором и пайплайном UI-15. При отклонении правки состояние возвращается в редактор, принятый снимок меняется по подтверждённому REST/WSS. Удаление связи из текста само по себе не доказывает разрешение на физический DELETE: вложение могло быть повторно использовано.
- UI-16 получает самостоятельный контракт для сохранения набора ссылок в черновике и срока жизни подготовленных файлов. Начальный UI-15 ведёт выбранные файлы, загрузки и путь только в рамках активного редактора, передаёт готовые ссылки в outbox. На интеграции UI-16 проверяем сохранение текста и draft-ревизии при изменении вложений и при очистке отправленного снимка. Для MSG-FILE-010 проверяем вместе с E2EE недоступность превью без ключа, зачистку в памяти при потере ключа и отдельный отказ ACL при корректной расшифровке.

## Итоговые проверки

- Использовать штатные входы, синтетические личку, явную тему и аккаунты A/B. Core fixtures и HTTPS/WSS loopback для ACL/realtime, GPUI для взаимодействия, геометрии и фокуса, один нативный прогон для OS picker, визуальной компоновки, ввода и фокуса. Проверить API GPUI 0.2.2 для ограниченного декодирования, отмены и сохранения фокуса до добавления зависимостей. Действующий профиль, SQLite/CLI и текстовый сценарий проходят регрессионные тесты.
- На итоговом SHA выполнить `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`, `cargo test --workspace --no-default-features`, `cargo test -p workspace-desktop --features gpui-test --all-targets`. Логи и кадры для прогона держать в синтетической папке вне Git. Набор сценариев подтверждает те же метаданные, что видит пользователь, отказ с доступным следующим шагом, правильный контекст, сохранение прокрутки и возврат фокуса.
- Для всего UI-15 остаются обязательны разработка и прогон, уточнение лимита и политик незавершённой загрузки и хранения. Доступ к E2EE и редактирование связей зависят от отдельных контрактов. Точная визуальная сверка и поведение загрузки в провайдерских каналах требуют собственных синтетических сценариев.
