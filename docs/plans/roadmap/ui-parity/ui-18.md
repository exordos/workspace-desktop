Для поведения используем оригинал `workspace_ui@af0999886daaffefc2a7be33f8dcf3f484a0e9c1`. В таблицах указаны наблюдаемые сценарии из его тестов. Для API используем контракт авторизации Desktop и `workspace_backend@bc986e07981737f57eeb5b205a5bee25c42e8858`. Макет и чистые кадры открытых общих экранов ещё не замерены. Перед конкретной реализацией повторить методику UI‑01…03 с синтетическими состояниями, одинаковым языком, темой и размерами окна, сверив готовый вариант через [Workspace Desktop Figma Bridge](../../../../skills/workspace-desktop-figma-bridge/SKILL.md). ## Возможности на базовом SHA

- [CLI](../../../../crates/workspace-desktop/src/bin/workspace-auth.rs) вызывает `Auth::begin_login`, `complete_login`, `cancel_login` и `logout`. Пароль и OTP читает интерактивно, проект выбирает числом из списка. `workspace-auth sync` и штатное окно используют общий Bootstrap. [Контракт авторизации](../../modules/auth.md) · [Контракт платформы](../../modules/shell-platform.md)
- [GPUI Client](../../../../crates/workspace-desktop/src/gpui_client/client.rs) получает снимок аккаунтов из `RuntimeClient`, показывает загрузку, признаки проблем со входом и переключатель. Пустой профиль предлагает вход через CLI. Штатное окно не ведёт форму входа, выход, собственный профиль или настройки. `Shell` проверяет поколение при смене аккаунта и закрывает прежний разговор. Тест `account_control_replaces_sidebar_content` проверяет уже подключённый переход.
- [Worker runtime](../../../../crates/workspace-desktop/src/gpui_client/runtime.rs) открывает один `Auth` вместе с адаптерами профиля и секретов. Через подписку `Auth` ядро запускает фоновые задачи и каталог для активного поколения. Рабочий Tokio использует один поток. Синхронный IAM через `reqwest::blocking` следует исполнять на ограниченном управляемом исполнителе блокирующих операций, включая завершение уже начатых записей при выходе приложения. Прямая синхронная операция внутри `RuntimeClient::request` заблокирует фоновый цикл.
- Тема берётся из `Window::appearance()`, в `ui/theme.rs` есть светлая и тёмная Blue Mist, изменение вида окна уже перерисовывает дочерние экраны. Сочетания регистрируются в `gpui_client/mod.rs`, редакторе, сайдбаре и верхней панели. Есть также прямые обработчики клавиш истории и Enter редактора. В UI‑10 подтверждены обход и ввод, остаются ограничения VoiceOver и масштабирования. [Приёмка UI-10](../gpui-ui-parity-accessibility.md)

Дальше пути `gpui_client/*` и `platform/*` относятся к `crates/workspace-desktop/src`, пути `auth/*`, `iam_http.rs` и `directory/*` относятся к `crates/workspace-core/src`. Новые файлы в таблицах задают рабочие границы, а изменения объявлений модулей и общей оболочки назначает оркестратор.

Сохранение проверять через временный каталог и атомарную замену файла. `gpui_client/mod.rs`, `client.rs`, `ui/top_bar.rs` и вызовы палитры у дочерних экранов передать одному владельцу на этапе подключения. Для отдельных экранов использовать один эффективный режим, чтобы исключить частичную перекраску после изменения настройки.

### Сочетания клавиш в PREF-005

- Desktop держит реестр стабильных ID типизированных действий, их локализованные подписи, области действия и комбинации по умолчанию. Настройки хранят только отклонения `назначено`/`отключено`, отсутствие записи даёт текущий default. Сброс одной команды и всех команд удаляет соответствующие отклонения. В первом срезе хранилище относится к профилю Desktop, версия формата и миграция выдерживают старые и неизвестные ID. В тесте перезапуска старый набор обновляется без потери остальных настроек.
- До подключения UI составить список `KeyBinding` и прямых обработчиков в `gpui_client/{mod,conversation,sidebar}.rs`, `composer/editor.rs` и `ui/top_bar.rs`. Преобразовывать только команды, у которых уже есть штатная точка вызова, и дополнять реестр при интеграции UI‑14. Нативные системные сочетания, буфер обмена, Tab/Escape в диалогах и ввод текста сохраняют приоритет. Конфликт в пересекающихся контекстах показывается до записи, одинаковое сочетание в доказанно непересекающихся контекстах допустимо. Для записи выделяется область фокуса, где клавиши не запускают команды окна.
- Учитывать Cmd/Ctrl, Option, Shift, Fn и раскладку через доступное событие GPUI. В GPUI 0.2.2 `Keystroke` различает ключ сопоставления, фактический символ и модификаторы. Требование к физическим клавишам подтвердить в английской и русской раскладках. Сочетания, которые macOS удерживает за собой, не обещать переназначать. Поведение одиночных сочетаний проверить прежде расширения до последовательностей и других платформ.
- При активной IME композиции, выделении, пароле или области записи сочетания не перехватывают набор. После Save, Disable, Reset или Cancel фокус возвращается к строке команды. Одна операция обновляет проверенную карту для всего окна, сохраняя неизменяемые GPUI и системные привязки. `App::clear_key_bindings` очищает весь набор, поэтому способ обновления требует короткой проверки GPUI перед выбором реализации.
- Границы агента: `gpui_client/hotkeys.rs` и его локальные тесты, экран `settings/hotkeys.rs`, запись через владельца `platform/preferences.rs`. Чистая проверка карты и коллизий может идти параллельно с другими карточками. Подключение `mod.rs`, `composer/editor.rs`, `conversation.rs` и `ui/top_bar.rs` согласовать с UI‑13/14/16 и владельцем настроек. Для GPUI проверить смену связи без рестарта, сохранение отклонений, конфликт, отказ записи, сброс, область редактора, отсутствие двойного действия и возврат фокуса. Нативно проверить EN/RU, Cmd/Option и IME в одном окне.

## Порядок делегирования и приёмка

1. Первым без сетевых изменений можно выделить PREF‑002: локальный файл, эффективная палитра и тесты чтения/записи в отдельном worktree. Параллельно агент входа готовит discovery, цепочку попытки и форму в своих файлах. Обоим достаточно заранее знать границу Shell, регистрацию в верхней панели выполняет общий владелец последовательными коммитами. Приоритет рабочего входа остаётся P0.
2. После входа агент аккаунтов подключает добавление и целевой повторный вход, затем выход конкретного поколения. После read-model UI‑13 агент профиля подключает свой GET и отдельный экран. Подготовку GPUI состояний можно вести заранее по согласованному типу профиля. Правка IAM ждёт собственного серверного контракта, аватары ждут политики загрузки.
3. PREF‑001 и чистая карта PREF‑005 готовы к параллельной работе после формата предпочтений. Действия сообщений из UI‑14 и ввод/фокус UI‑16 подключаются к реестру после приёмки соответствующих изменений. Общие точки `client.rs`, `mod.rs`, `runtime.rs`, `ui/top_bar.rs`, `contracts.rs` и `client/loopback.rs` закрепляются по одному владельцу на интеграционный коммит. UI‑17 воспроизводит базовые проверки независимо.

Принимаем UI‑18 по готовым карточкам с источником, действием, видимым исходом, точками входа и уровнем проверки. Реализация каждого среза начинается из принятого SHA. В её тестах использовать тестовый `Auth` и `SecretStore`, локальное HTTPS и временный профиль; штатный CLI проверяется отдельно от GPUI. Логи используют `op_id` и статусы, без паролей, OTP, токенов, тела ответа API и данных профиля. После реализации выполнить fmt, два режима Clippy, workspace, headless и `gpui-test` из [AGENTS.md](../../../../AGENTS.md). Для текущей карточки достаточно ревью планов, ссылок и `git diff --check`. Окна, IAM стенда и нативные действия в рамках проверки плана не запускались.
