# Реализация UI-13–18

База — принятая UI-12 на `fafcd6329bfc53a53b610dbb1a723c971f5a3f0e`. [Общий план паритета](../gpui-ui-parity.md) задаёт пользовательские сценарии. Электронный клиент `af099988` определяет наблюдаемое поведение. Модули, обмен данными и проверки проектируются по контрактам Workspace Desktop и подтверждённому API.

## Соседний сценарий исходящей очереди

Карточка [отрисовки содержимого исходящего сообщения](outgoing-message-content.md) продолжает UI-15 и CALL-005: медиа и звонки должны сохранять конечный вид, пока запись ожидает подтверждения.

## Доработки Workspace для переноса

В [заметках о доработках Workspace](workspace-followups/README.md) собираются сценарии и детали поведения, которые нужно учитывать при реализации Desktop. [Горячие клавиши](workspace-followups/hotkeys.md) фиксируют поиск и переход в канал через `Ctrl/Cmd+K`.

## Порядок интеграции

1. Параллельно запустить первый срез UI-13, хранилище черновиков UI-16 и проверочный набор UI-17. UI-13 владеет общим экраном, REST-декларациями и его сценарным тестом. UI-16 работает в `storage` и его тестах. UI-17 владеет командами проверок и документацией.
2. После принятия UI-13 отдельно подключить серверную команду UI-14 и редактор черновиков UI-16. У команды удаления и квитанций один владелец `messenger/rest.rs` и `messenger/mod.rs`. Подключение черновиков к редактору не требует менять эти точки одновременно.
3. После готовности команды удаления можно параллельно готовить её меню и авторизованное чтение вложений. Интеграцию в `conversation.rs` и `history/viewport.rs` делать по очереди. Один владелец проектирует типизированный разбор ссылок Markdown для цитат, пересылки и файлов. Граница прочитанного подключается после согласования формы истории, событий и проверки активности окна.
4. Для следующих шагов держать отдельными задачи, которые меняют редактор, подготовку отправки, очередь или события. Один владелец меняет общую точку подключения на принятой базе. Изолированные модули и их тесты могут готовиться параллельно.

Каждый шаг получает worktree от принятого SHA, владельца файлов и узкие проверки. Сценарий проверяется от штатной точки входа. Перед отметкой приёмки повторяются затронутые проверки на интегрированном SHA. Нативные действия идут в одном тестовом экземпляре с синтетическими данными. Подтверждения, ограничения и SHA записываются в `JOURNAL.md`.
