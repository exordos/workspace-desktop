# Отрисовка исходящего сообщения в Workspace Desktop

[Отправка и очередь](../../modules/messenger-send.md) · [Вложения](../../modules/messenger-files.md) · [CALL-005](../../features/sections/calls.md#call-005) · [UI-15](ui-15.md)

## Результат итерации

Пока сообщение находится в очереди, история выбирает его представление по содержимому так же, как после подтверждения. Статус влияет на подпись и отметку доставки, но не превращает карточку звонка, вложение или ссылку Workspace в обычный текст. Тот же публичный UUID остаётся одной строкой при переходе из очереди в подтверждённую историю.

Владелец, тема и поколение входа остаются частью доступа к вложению. Текст E2EE раскрывается только через уже выданное Core разрешение на чтение. Действия, требующие серверного сообщения, остаются закрыты до подтверждения.

Видимый сбой сейчас подтверждён для Jitsi и вложений. Для упоминаний, ссылок Workspace, ответов и пересылок отдельного ограничения очереди не найдено: их presentation проходит через уже существующий Markdown-разбор. Кнопки действий, которые меняют серверную строку, не должны включаться только из-за того, что исходящая строка теперь получила карточку.

## Владельцы и план реализации

1. **Core и хранилище медиа.** Обычный Markdown проверяется по точному снимку очереди. Для E2EE Core читает точный шифротекст, сверяет ключ и устройство, расшифровывает через текущую активацию и разрешает только прямой UUID вложения. При подтверждении переход допускается для совпадающей записи истории; смена ключа, удаление снимка или отзыв доступа закрывают fence.
2. **История GPUI.** Для обычной строки очереди строить `Body` и `MediaReference` тем же разбором, что для истории; передавать медиа существующим карточкам. Для защищённой строки использовать уже раскрытое разрешённое тело. Оба вида Jitsi сразу получают отдельную карточку, а действие входа включается только после подтверждения.
3. **Проверка границ.** Не открывать чужой файл, ссылку из fenced code или произвольную внешнюю ссылку как Workspace-файл/звонок. Ожидающие файлы не попадают в галерею; после подтверждения сохраняется проверка владельца, темы, ключа и исходного содержимого.

## Критерии приёмки

- При отправке ссылки Jitsi в обычном и защищённом чате карточка видна сразу, вместе с подписью очереди. Нельзя обойти проверку подтверждения, сессии или ключа.
- При отправке изображения/видео появляется медиа-карточка в составе пузыря, а для прочих файлов — карточка вложения, в обычной и защищённой очереди. Подпись смешанного медиа-сообщения остаётся на месте. Превью использует файл из текущей очереди и текущего владельца.
- Упоминания, даты и ссылки Workspace, ответы и пересылки сохраняют видимые карточки и форматирование при состояниях `Waiting`, `Sending`, `Unknown` и отказе.
- После серверного подтверждения остаётся одна строка с тем же UUID. При потере связи содержимое не исчезает и отображает текущий статус доставки.
- Poll не отображается как Markdown-сообщение и остаётся отдельной функцией.

## Проверка

План проверки включает GPUI-сценарии: обычный текст, Jitsi, одиночная и смешанная картинка, видео и файл в обычном и защищённом сообщении, упоминание, ответ, пересылка, неопределённый исход и подтверждение без дубля. Для Core проверить чтение вложения только через точный URN обычной очереди или прямую ссылку в расшифрованном E2EE-снимке, удаление/смену темы и смену поколения входа. При интеграции фиксировать фактически выполненные команды и случаи, не проверенные в нативном окне.

## Результат и проверка

- Реализованы Core-доступ к медиа обычной и защищённой очереди и общий выбор Jitsi-карточки для исходящих строк. Mentions, ссылки Workspace, ответы и пересылки используют уже общий разбор Markdown/защищённого тела.
- Не добавлены и не запускались автотесты, сборка или нативная визуальная проверка. После разрешённого запуска следует пройти сценарии из раздела «Проверка» и записать фактический результат.
