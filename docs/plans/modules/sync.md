# `core::sync`

Родительские документы — [архитектура Workspace Desktop](../workspace-desktop-architecture.md) и [план проекта](../workspace-desktop.md). Входной контракт — [передача событий из `runtime`](runtime.md#как-событие-доходит-до-sync).

`sync` принимает событие, выбирает обработчики и согласованно сохраняет изменения и позицию в потоке. `runtime` управляет задачей, адаптер знает протокол сервиса, а раздел определяет, как событие меняет его данные. Активный и фоновые аккаунты проходят один путь обработки.

Сценарии разделов собраны в [карте функций](../workspace-desktop-features.md).

## Что приходит из `runtime`

Задача источника вызывает `sync` и ждёт результата перед обработкой следующего события своего потока. Передаёт контекст аккаунта, организацию, проект и пользователя, идентификатор источника, поколение сессии, тип и данные события. Если протокол даёт позицию, передаёт и её. Для мессенджера это пара `epoch_generation` и `epoch_version`. Адаптер также передаёт режим доставки, чтобы события догрузки обновляли данные без системных уведомлений.

Один логический поток мессенджера использует общий курсор для REST-догрузки и WebSocket. Ключ курсора — контекст и источник. Поколение локальной сессии используется для проверки записи, а `epoch_generation` относится к серверному потоку. События из разных потоков могут обрабатываться одновременно, а запись общих данных должна сохранять согласованность.

## Как выбираем обработчики

Маршруты объявляем явно. Аналог в TypeScript — `switch` по типу события. Для мессенджера сначала смотрим на `object_type` и `action`, затем на `payload.kind`, если нужно уточнить действие. Например, `message.created` передаём мессенджеру, `user.updated` — каталогу пользователей, `file.deleted` — обработчику метаданных и файлового кэша. Для почты и календаря добавим маршруты по контрактам их источников.

Одно событие может вызвать несколько обработчиков. Например, новое сообщение меняет кэш сообщений и может изменить счётчик непрочитанных по правилам мессенджера. Реакции, счётчики и другие обработчики подключаются отдельно для тестовых прогонов на изолированных данных. Отзыв доступа и очистка защищённого кэша обязательны. Если событию нужны дополнительные данные, обработчик решает, запросить их сейчас или сохранить отметку об устаревших данных для последующего обновления. [Фоновая обработка и замеры](../workspace-desktop-architecture.md#фоновая-обработка-и-замеры)

## Пример с `message.created`

[Обработчик мессенджера](messenger.md#от-события-к-записи) описывает, какие изменения он передаёт в транзакцию. [Контракт хранилища](storage.md#сообщение-и-курсор-в-одной-транзакции) описывает её границы и результат при сбое.

Для собственного сообщения тот же обработчик может закрыть [запись очереди отправки](messenger-send.md#как-избегаем-дублей) в транзакции с сообщением и курсором.

После записи `SyncChange::OutboxChanged` просит оболочку перечитать очередь, даже когда сообщение уже лежало в SQLite. HTTP и GET закрывают подтверждённую запись через тот же механизм хранилища и публикуют изменение без продвижения курсора. Правка, удаление и отзыв доступа становятся видны оболочке после успешного применения события.

В окне открыт календарь A. Задача мессенджера B получает новое сообщение на позиции `124` и передаёт его в `sync`. Последняя сохранённая позиция этого потока — `123`.

1. `sync` сверяет контекст, поколение сессии и позицию с сохранённой. Повтор `123` в том же поколении потока оставит данные и курсор без изменений.
2. Обработчики мессенджера применяют сообщение к данным B и определяют изменение сводки. Если из события нельзя вывести точный счётчик, используем авторитетные данные Workspace вместо безусловного `+1`.
3. Перед записью `sync` ещё раз проверяет, что поколение сессии имеет право на запись. Изменения всех включённых обработчиков и позиция `124` фиксируются одной транзакцией хранилища. Если обработка или запись не удалась, сохранённая позиция остаётся `123`, поэтому источник может повторить обработку.
4. После фиксации оболочка получает изменение сводки B. Системное уведомление возможно только для живого события после `ready` и по правилам мессенджера. Уведомление ведёт в разговор B. Календарь A остаётся открытым до действия пользователя.

## Восстановление и проверка

- При сигнале о разрыве последовательности адаптер догружает пропущенное с последнего сохранённого курсора. Для истёкшего курсора он восстанавливает серверные снимки и сбрасывает затронутый производный кэш по контракту источника. Сетевой протокол остаётся у адаптера. [Контракт Workspace Messenger](../../../../workspace_backend/docs/ru/workspace_ui_realtime_integration.md)
- Незнакомое событие в корректном конверте можно пропустить по контракту источника и зафиксировать как обработанное. В журнале остаются тип и версия. Ошибка применения поддерживаемого события сохраняет предыдущий курсор.
- В тестах проверяем повтор события, сбой записи между обработчиками, выход из B до фиксации и догрузку без уведомлений. Отдельно проверяем, что обновление B видно в сводке, пока открыт A, а изолированный прогон с отключённым обработчиком оставляет рабочий курсор без изменений.
