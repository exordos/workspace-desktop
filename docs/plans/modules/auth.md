# `core::auth`

Родительские документы — [архитектура Workspace Desktop](../workspace-desktop-architecture.md) и [план проекта](../workspace-desktop.md).

`auth` владеет сессиями, получает и обновляет токены и сообщает, какие контексты авторизованы. `runtime` решает, для каких из них запустить фоновые задачи. Оболочка отдельно хранит выбранный в окне аккаунт.

## Хранение и восстановление

- **Аккаунт** — сохранённая учётная запись в конкретном экземпляре Workspace. Локально храним её идентификатор, адрес экземпляра и метаданные для восстановления входа.
- **Сессия** — состояние входа этого аккаунта. В памяти держим реестр сессий, примерно как `Map<AccountId, Session>` в TypeScript. У каждой сессии есть поколение, статус и доступные контексты. Контекст определяет организацию, проект и пользователя в экземпляре Workspace.
- **Учётные данные** — токен доступа, срок его действия и данные для обновления. Токен доступа держим в памяти, секреты для восстановления входа — в защищённом хранилище ОС через `desktop::platform`. Ключ выдачи токена учитывает контекст и сервис, для которых он запрошен.

При запуске `auth` восстанавливает аккаунты независимо. Контекст становится доступен фоновой работе, когда для него подтверждена сессия. Если аккаунту B нужен повторный вход, аккаунт A продолжает работу.

## Получение и обновление токена

1. Задача запрашивает токен, явно передавая контекст и сервис. Если действующий токен скоро истекает, `auth` обновляет его.
2. Все запросы, использующие один и тот же refresh-токен, ждут одного обновления. Аналог в TypeScript — `Map<CredentialKey, Promise<RefreshResult>>`, где ключ идентифицирует набор учётных данных. Если один запрос отменился, остальные продолжают ждать результат.
3. При успехе `auth` проверяет, что результат относится к текущему поколению сессии. Если сервер выдал новый refresh-токен, `auth` сохраняет его до публикации обновлённого состояния. Фиксация результата и выход из аккаунта выполняются последовательно для одного аккаунта, чтобы запоздавший ответ не восстановил удалённые данные.
4. При временном сбое повторяем запрос с паузой. После истечения токена сетевые операции ждут обновления. Если IAM окончательно отклонил данные для обновления, `auth` переводит затронутый контекст в состояние «нужен повторный вход».

## Связь с `runtime`

[Жизненный цикл фоновых задач](runtime.md) описывает, как `runtime` использует состояние `auth` и передаёт события в `sync`.

Два механизма, оба внутри процесса. **Прямой вызов** возвращает токен фоновой задаче. **Подписка на состояние**, как `store.subscribe()` в TypeScript, отдаёт `runtime` текущий снимок при подключении и последующие изменения. В снимке есть доступные контексты, поколение сессии и версия токена для соответствующего сервиса. Секреты выдаются через прямой вызов.

| Изменение в `auth` | Реакция `runtime` |
| --- | --- |
| Вход или восстановление сессии | Сверяет актуальные контексты со своими задачами и запускает недостающие. |
| Обновление токена | Для Workspace Messenger получает новый токен и переподключает WebSocket. Поколение сессии и курсор синхронизации сохраняются. |
| Выход или потеря доступа | `auth` отзывает разрешение на запись для затронутого контекста до публикации снимка. `runtime` останавливает задачи. Повторный вход получает новое поколение. |

Дальше события идут по цепочке `runtime` → `sync` → обработчик раздела → хранилище → обновление интерфейса. При переподключении мессенджер догружает пропущенные события с сохранённой позиции. [Путь события в архитектуре](../workspace-desktop-architecture.md#путь-события) · [Контракт событий Workspace Messenger](../../../../workspace_backend/docs/ru/workspace_ui_realtime_integration.md)

## Проверка перед подключением к интерфейсу

- Восстановление двух аккаунтов при запуске. Повторный вход для B не прерывает работу A.
- Несколько запросов с одним refresh-токеном ждут одного обновления и получают актуальный результат.
- Временный сбой допускает повторную попытку. Окончательный отказ IAM останавливает задачи только затронутого контекста.
- После выхода запоздавший ответ на обновление не возвращает сессию. Повторный вход запускает задачи нового поколения.
- Успешное обновление токена мессенджера переподключает WebSocket с сохранённым курсором.

Точные контракты выдачи токенов для почты и календаря уточняем при проектировании этих разделов.

## План реализации первого среза без GUI

Результат первого среза — два аккаунта можно независимо подключить к Workspace Messenger, выбрать проект для каждого, восстановить сессии после перезапуска, обновить токены и выйти из выбранного аккаунта. На одну запись аккаунта сохраняем один выбранный проект. Проверяем сценарий через интеграционные тесты и ручной терминальный прогон на тестовом стенде.

### 1. Создать Cargo workspace и определить контракты

- Добавить корневой `Cargo.toml` и два пакета в `crates/`. В `workspace-core` разместить `context` и `auth`. В `workspace-desktop` разместить системные адаптеры в `platform` и точку сборки зависимостей для прогона без окна. `workspace-desktop` зависит от `workspace-core`.
- В `context` определить `AccountId`, `OwnerContext` (аккаунт, экземпляр Workspace, организация, проект, UUID пользователя) и `SessionGeneration`. Общий тип контекста затем используют оболочка и фоновые задачи. В `auth` определить операции `begin_login`, `complete_login`, `restore`, `access_token` и `logout`. Выбор проекта получает список проектов и идентификатор попытки. Подписчики получают снимок сессий и версии токенов, доступ к токену выдаёт `access_token(context, service)`.
- Определить интерфейсы `IamClient`, `AccountStore` и `SecretStore` в `workspace-core`. Добавить реализации для тестов в памяти, управляемое время для проверки истечения токена и короткий `AGENTS.md` с командами проверок.

### 2. Реализовать вход и выбор проекта

- Нормализовать HTTPS-адрес Workspace и привязать запросы с паролем, OTP и токенами к этому серверу. Сверить с веб-клиентом два шага IAM. `begin_login` запрашивает базовый токен по логину, паролю и при необходимости OTP, затем получает список проектов. `complete_login` проверяет принадлежность проекта списку этой попытки и запрашивает токен с правами выбранного проекта. [Запросы IAM](../../../../workspace_ui/packages/web/src/shared/api/workspace-iam-auth.ts) · [Двухшаговый вход](../../../../workspace_ui/packages/web/src/entities/workspace-auth/workspace-auth.lib.ts#L725)
- До выбора проекта держать промежуточные токены в памяти. Пароль и OTP нужны только для запроса входа. Отмена и истечение срока попытки сбрасывают её данные. Аккаунт становится активным после подтверждения пользователя, проекта и организации по данным IAM и успешного сохранения сессии. Источник идентификатора организации, ответы для OTP и ошибки входа уточнить на стенде.

### 3. Подключить хранение и восстановление

- Сохранять `AccountId`, контекст и ссылку на секрет в локальном реестре. Для первого прогона использовать атомарно обновляемый файл метаданных и системное хранилище секретов macOS. В нём держать refresh-токен. Access-токен, пароль и OTP исключить из файлов и журналов.
- При входе сначала записать секрет, затем зафиксировать запись аккаунта. При повторном входе переключить запись на новый секрет после его сохранения и очистить старый. При сбое записи реестра сохранить прежнюю запись и удалить новый секрет. При старте восстанавливать только аккаунты, на которые указывает реестр.
- Для каждого сохранённого аккаунта независимо получить секрет и подтвердить токен для его контекста. Отсутствующий или окончательно отклонённый секрет требует повторного входа. Временная недоступность IAM или хранилища допускает повтор. Сбой B не задерживает публикацию готовой сессии A.

### 4. Реализовать обновление и выход

- Запросы с одним набором учётных данных ждут одного обновления. Отмена одного ожидающего запроса не отменяет обновление для остальных. До истечения срока можно выдать действующий access-токен, если IAM временно недоступен. После истечения ждём обновление с паузой между попытками. Контракт IAM определяет, какие ошибки требуют повторного входа.
- Сетевой запрос выполнять отдельно от фиксации. Для одного аккаунта сериализовать фиксацию результата и выход. При фиксации сверить поколение и записать новый refresh-токен, если IAM его выдал. Опубликовать токен и его версию после записи. Если запись не удалась, повторять сохранение полученного секрета, пока текущая сессия его держит в памяти. При перезапуске пробуем восстановить сессию по сохранённому секрету и предлагаем повторный вход, если IAM его уже отклонил. На стенде проверяем поведение ротации и признаки окончательного отказа.
- При выходе прекратить выдачу токенов этого аккаунта и сменить поколение. Зафиксировать в реестре состояние, исключающее восстановление, затем удалить секрет. При ошибке записи реестра сообщить, что выход ещё требуется завершить. При ошибке удаления секрета сохранить запись для повтора очистки. Запоздавший результат входа, восстановления или обновления не может активировать завершённую сессию. Первый срез принимает локальный выход за базовый сценарий. Возможность серверного отзыва токена проверяем на стенде.

### 5. Проверить готовность среза

- `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings` и `cargo test --workspace` проходят без GUI и доступа к стенду. Контрактные тесты HTTP-адаптера покрывают вход с OTP, выбор проекта и ответы IAM при обновлении.
- Интеграционные тесты проверяют вход и отмену выбора, восстановление в новом экземпляре `auth`, изоляцию двух аккаунтов, одно обновление при параллельных запросах, ротацию токена и сбой записи. Отдельный тест задерживает ответ обновления до выхода из B и повторного входа. Старый ответ не меняет новую сессию B, а A продолжает получать токен.
- Ручной прогон на тестовом стенде использует настоящее системное хранилище. Пароль и OTP вводятся интерактивно. Входим под двумя аккаунтами и выбираем проект для каждого. После перезапуска получаем токен после обновления и выполняем с ним запрос к Messenger. Выходим из одного аккаунта и перезапускаемся ещё раз. Второй аккаунт восстанавливается, а сессия и секрет первого удалены.

## Запуск без окна

На macOS соберите `cargo build -p workspace-desktop --no-default-features --bin workspace-auth`. Перед проверкой задайте отдельный каталог для метаданных тестовых аккаунтов. Refresh-токены хранятся в Keychain.

```sh
export WORKSPACE_AUTH_STATE_DIR="$(mktemp -d)"
server='https://workspace.example.com'
target/debug/workspace-auth login "$server"
target/debug/workspace-auth login "$server"
target/debug/workspace-auth status
```

Подставьте адрес тестового стенда в `server`, затем идентификаторы двух аккаунтов из `status` в `account_a` и `account_b`. Команда `verify` выполняет запрос к Messenger с токеном выбранного аккаунта. Каждая команда запускает новый процесс. После выхода из B `status` должен показать только A.

```sh
target/debug/workspace-auth verify "$account_a"
target/debug/workspace-auth verify "$account_b"
target/debug/workspace-auth logout "$account_b"
target/debug/workspace-auth status
target/debug/workspace-auth logout "$account_a"
```
