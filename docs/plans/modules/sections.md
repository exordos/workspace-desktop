# Общий контракт `core::sections`

Родительские документы — [архитектура Workspace Desktop](../workspace-desktop-architecture.md) и [план проекта](../workspace-desktop.md). Смежные контракты — [runtime](runtime.md), [sync](sync.md), [storage](storage.md) и [оболочка](shell-platform.md).

Раздел владеет своими данными и правилами. При сборке приложения явно подключаем его обработчики событий, чтение сводки и открытие целей. Для первого этапа достаточно этих трёх операций. Их названия ниже иллюстрируют контракт, как сигнатуры функций в TypeScript.

## Три операции

| Операция | Что получает раздел | Что делает и возвращает |
| --- | --- | --- |
| `applyEvent` | Контекст владельца, поколение сессии, типизированное событие, режим доставки и транзакцию `storage` для этого контекста. | Применяет изменения и сообщает, изменилась ли сводка, есть ли кандидат на уведомление и нужна ли дополнительная загрузка. Ошибка обработки откатывает запись события. |
| `readSummary` | Контекст владельца. | Возвращает актуальную сводку раздела из зафиксированных данных. Например, счётчик непрочитанного. Сводку можно перечитать при запуске или после пропущенного обновления. |
| `openTarget` | Контекст владельца и типизированную цель раздела. | Проверяет доступ к объекту и подготавливает данные для открытия. Возвращает доступный объект с данными для экрана либо результат «нет доступа», «объект отсутствует» или «нужно повторить загрузку». |

### Применение и публикация

`runtime` передаёт событие в `sync`. `sync` проверяет контекст и повтор, выбирает обработчик по источнику и типу события и вызывает его. Раздел пишет через полученную транзакцию. `sync` сохраняет в ней курсор, если источник его поддерживает. Дополнительные сетевые запросы выполняются за пределами транзакции. Если без догрузки данные пока неполные, раздел может сохранить признак, что их нужно обновить. [Маршрутизация](sync.md#как-выбираем-обработчики) · [Транзакция](storage.md#сообщение-и-курсор-в-одной-транзакции)

После фиксации `core` публикует изменившуюся сводку по ключу «контекст + раздел». Сводка содержит актуальное значение, поэтому оболочка может объединить несколько обновлений и отобразить последнее. Кандидат на уведомление передаётся отдельным действием после фиксации. События догрузки могут изменить сводку. Баннеры доступны для живых событий по правилам раздела и оболочки. Активный и фоновые аккаунты проходят один путь обработки. [Сводки в оболочке](shell-platform.md#обновление-счётчика-фонового-аккаунта)

### Открытие цели

Цель содержит исходный контекст, идентификатор раздела и данные для открытия объекта. Оболочка проверяет доступность контекста через `auth` и передаёт маршрут экрану раздела. Экран запрашивает данные у раздела в `core` через операцию открытия цели. Раздел проверяет доступ к объекту и при необходимости догружает данные. Оболочка меняет маршрут только для актуального перехода. Если пользователь уже выбрал другой экран, поздний результат не переключает окно. [Маршрутизация в оболочке](shell-platform.md#маршрутизация-в-оболочке)

## Вызовы между разделами

Три операции выше описывают общий контракт синхронизации и оболочки. Для чтения и записи бизнес-объектов каждый раздел предоставляет собственные типизированные операции в `core`. Например, создание события входит в API календаря, а отправка сообщения — в API мессенджера. Внутри процесса можно напрямую вызвать доступный метод модуля. Адаптер сервиса, хранилище, проверка данных и правила записи остаются у владельца.

| Что связываем | Как работает контракт |
| --- | --- |
| Действие пользователя | Сценарий вызывает операцию владельца и получает результат или ошибку. Если нужны несколько модулей, функция сценария в `core` явно получает их как зависимости и вызывает их операции. Собственный экран раздела и внешний сценарий используют один и тот же путь записи. |
| Реакция на изменение | Владелец публикует типизированное событие после подтверждения изменения. Сценарий явно подключает обработчик и при необходимости вызывает операцию другого владельца. Входящие события сервисов по-прежнему применяет `sync`. |
| Переход к объекту | Передаём типизированную цель с контекстом, разделом и идентификатором. Оболочка ведёт маршрут, а модуль-владелец проверяет доступ и открывает объект через `openTarget`. |

Команды и события между разделами несут `OwnerContext` и `SessionGeneration` исходной сессии. При смене выбранного аккаунта ответ остаётся привязан к исходному контексту. При выходе или новом входе результат старого поколения отбрасывается. Каждый владелец получает доступ к своему сервису через `auth` и проверяет права на свой объект. Между разделами передаём ссылку и только те поля, которые нужны и разрешены для передачи в конкретном сценарии.

Для действий с записью в двух сервисах каждый отвечает за собственное подтверждение. Если исходное изменение сохранено, а доставка во второй раздел не удалась, результат остаётся у первого владельца. Сценарий определяет, как показать сбой и повторить доставку. Для защиты от дублей используем устойчивый идентификатор операции или события. При запоздавших событиях учитываем версию либо сверяем актуальное состояние у владельца. Если по требованиям действие должно срабатывать при закрытом Desktop, место выполнения и гарантии доставки определяем на стороне сервисов. [Условные примеры](../workspace-desktop-architecture.md#условные-примеры-взаимодействия)

## Мессенджер и тестовый раздел

| Шаг | Мессенджер | Тестовый раздел |
| --- | --- | --- |
| Применить событие | `message.created` для B добавляет сообщение и обновляет данные разговора. Точное непрочитанное берём из подтверждённых данных. | Тестовый источник присылает `item.created` для B. Обработчик сохраняет запись по ID. |
| Опубликовать сводку | После фиксации оболочка получает счётчик мессенджера B и при подходящих условиях — кандидата на баннер. | После фиксации оболочка получает количество записей тестового раздела B. Для проверки навигации живое событие может дать кандидата на баннер. |
| Открыть цель | [Маршрут разговора](messenger.md#маршрут-разговора) задаёт последние сообщения или окно вокруг UUID. Мессенджер подтверждает доступ, читает и при необходимости догружает историю. | Цель содержит ID записи. Раздел возвращает сохранённую запись или сообщает, что она отсутствует. |

На первом прогоне в окне открыт тестовый раздел A. Событие мессенджера B обновляет его сводку, а клик открывает чат B. Для обратной проверки, пока открыт чат B, `item.created` для A обновляет сводку тестового раздела A. Нажатие открывает конкретную запись A. Так оба раздела используют один контракт, а правила хранения и открытия объекта остаются у каждого раздела. [Сценарий мессенджера](messenger.md#сценарий) · [План первого этапа](../workspace-desktop.md#первый-этап)

## Проверка

- Для обоих разделов проверить, что сбой записи сохраняет предыдущий курсор и не публикует сводку или баннер. Повтор уже применённого события не создаёт вторую запись.
- Проверить, что сводка появляется у исходного аккаунта, а текущий экран меняется только при переходе. При выходе из аккаунта устаревшая цель не открывает его данные.
