# Папки мессенджера

[Контракт мессенджера](messenger.md) · [Сценарии MSG-NAV-008–013](../features/messenger/navigation.md#папки) · [Дорожная карта](../roadmap/messenger-next.md#расширение-мессенджера)

Фундамент подключён в `workspace-core`. [Проверка](#что-проверено) охватывает REST, WebSocket и SQLite. GPUI относится к последнему этапу.

## Что делает оригинальный сайдбар

Референс — `workspace_ui` на `af099988`, `workspace_backend` на `bc986e0` и исходное состояние Desktop на `c01c3de`.

| Сценарий | Поведение референса |
| --- | --- |
| Системные папки | «Все чаты», «Личные» и «Каналы» имеют фиксированные UUID с окончаниями `0000`, `0001`, `0002`. Сервер строит состав по активным подпискам и исключает архив. В v2 все три могут прийти с `system_type: "all"`, поэтому тип уточняется по UUID. «Личные» включают приватные разговоры по серверным правилам. |
| Свои папки | Пользователь создаёт папку с названием и цветом, меняет их, удаляет папку после подтверждения, добавляет или убирает разговор. Один разговор может входить в несколько папок. Удаление папки или связи сохраняет сам разговор и историю. |
| Закрепление и порядок | Закрепление действует на элемент конкретной папки, в том числе системной. Сайдбар ставит закреплённые выше, затем применяет выбранный порядок (активность, алфавит или непрочитанное с учётом группировки). `order_index` участвует в сортировке, но отдельного изменения порядка через `PUT /folder_items/{uuid}` в маршрутах референса нет. |
| Список и поиск | Элементы папки связываются с каталогом по `stream_uuid`, темы берутся из каталога. Для «Все чаты» референс добавляет доступные активные чаты, которые ещё не попали в серверный снимок папки. Поиск в других папках использует общий список и убирает повторы по UUID разговора. |
| Панель папок | Вертикальный и горизонтальный вид, бейджи и быстрый поиск **по названиям папок** при переполнении вертикальной панели. Режим и флаг видимости системных папок хранятся в настройках клиента. В проверенной ревизии переключатель меняет флаг и подпись в меню, а фильтрация кнопок этим флагом не подключена. Выбор папки живёт в памяти. |

## Что переиспользует Desktop

- `messenger::catalog` загружает все страницы чатов и тем, скрывает архив, сохраняет снимок и защищает запись от смены поколения сессии и отзыва доступа. Этот каталог даёт имена, темы и маршруты строкам папок.
- `RestClient::collection` читает страницы по `X-Pagination-Marker`. `sync` уже принимает `folder.created/updated` для счётчика «Все чаты» и сохраняет его с курсором. При `ready` адаптер сверяет число через `GET /folders/{uuid}`. Счётчик Dock использует этот путь.
- `bootstrap` загружает обычный каталог независимо от журнала. Фоновый обработчик папок запускается через тот же `MessengerSource` после `ready`. Загрузки каталога одного владельца работают последовательно.

## Источник и модель данных

Сервер хранит папки на уровне пользователя и проекта. `MessengerSource::folders` даёт команды, подписку и снимок по владельцу и поколению. Core проверяет допустимость действий и строит список папки из связей и существующего каталога. `sync` принимает события, `storage` отвечает за транзакции, Bootstrap запускает обновление по сессии. Будущий GPUI передаёт команды и выбирает папку в рамках текущего аккаунта.

| Что читаем | Что используем |
| --- | --- |
| `GET /api/workspace/v1/messenger/folders/` | Все страницы папок с вложенными `folder_items`. Для папки нужны UUID, тип, название, цвет, порядок из коллекции, даты и абсолютный `unread_count`. Полный успешный снимок заменяет предыдущий. |
| `GET …/folders/{folder_uuid}` | Точечная сверка папки и её состава. `GET …/folder_items/?folder_uuid=…` оставляем для проверки совместимости или догрузки состава, если рабочая версия API требует этого. В обычном bootstrap вложенный состав приходит с папками. |
| Элемент папки | Свой UUID, UUID папки (`folder_uuid` или `folder`), UUID разговора, `chat_type` (`private`, `group`, `stream`), `pinned_at`, `order_index`, даты, `unread_count` и активная/пассивная части. Темы открываются через существующий маршрут разговора. |

На границе API нормализуем алиасы и системные UUID. Проверяем контекст авторизованного запроса и поля владельца, где сервер их возвращает. Во вложенных элементах проверяем проект, пользователя и совпадение ссылки на родительскую папку. Проверяем согласованность дубликатов и отличаем полный пустой состав от отсутствующего или некорректного поля. Незнакомый вид папки сохраняет безопасный доступ на чтение, право на изменение даём только подтверждённому пользовательскому типу.

В списке показываем только доступные активные разговоры из каталога этого владельца. Если связь пришла раньше разговора, сохраняем её и обновляем каталог. Для «Все чаты» дополняем список доступными активными разговорами без серверного элемента. Чаты без элемента пока нельзя закрепить. Для «Личных» и «Каналов» берём состав сервера. `Chat.direct` в Desktop различает личку один на один, а приватная группа тоже может попасть в «Личные». Папка меняет вид списка, а доступ к разговору подтверждает общий `ChatRoute`.

В референсе обычные списки папок скрывают чат с собой, в Desktop каталог включает его как «Избранное». Вопрос его размещения решаем перед приёмкой UI. Фундамент сохраняет серверную связь, если она есть.

Используем подтверждённые сервером счётчики. В проверенной серверной проекции счётчик папки складывается из активного непрочитанного. Значения разных папок пересекаются. Для бейджа «Все чаты» читаем имеющуюся сводку Core, которую использует Dock. Отсутствие подтверждённых данных представляем отдельно от нуля.

## SQLite, запуск и восстановление

- В существующей SQLite-базе профиля заводим таблицы папок и элементов. Ключи включают полный `OwnerContext` (аккаунт, сервер, организацию, проект и пользователя) и серверный UUID. Индексы нужны для чтения элементов одной папки, поиска связей по UUID разговора и удаления элементов папки одной транзакцией. Каталог чатов продолжает хранить имена, темы и прочие данные разговора.
- Для владельца храним признак наличия полного снимка, отметки о необходимости сверки и ревизию для защиты от запоздавших ответов. На старом профиле миграция добавляет таблицы с пустым кэшем папок. Уже сохранённый курсор не подтверждает полноту папок, поэтому при первом запуске обязателен полный запрос. Последний выбранный UUID, если сохраняем его после перезапуска, записываем как локальную настройку данного владельца. Для отсутствующей или скрытой папки выбираем «Все чаты» после получения полного состояния. Размещение панели и видимость системных папок тоже относятся к локальным настройкам.
- После подтверждения сессии Core даёт читать её последний пригодный снимок во время обновления и при временном сбое. Каталог чатов загружается независимо. Ошибка папок оставляет доступным обычный каталог и повтор загрузки. Частично полученные страницы и ошибочные ответы не заменяют пригодный снимок. Для первого запуска без подтверждённой сессии состояние папок остаётся неизвестным.
- Первую полную сверку начинаем после завершения догонки существующего источника. Сохраняем результат только при действующем поколении сессии и совпадении ревизии. После переключения аккаунта запоздавший ответ B может обновить только данные B, пока его сессия действует. При выходе устаревшее поколение теряет право на запись и публикацию. Для отображения всегда читаем данные активного `OwnerContext`.
- При обычном переподключении продолжаем с курсора, затем обрабатываем ожидающие сверку папки. При истёкшем курсоре, смене поколения журнала или сбросе источника снимаем отметку полноты, очищаем недостоверную проекцию папок этого владельца и увеличиваем ревизию в транзакции сброса. После догонки заново сверяем папки и доступность разговоров в каталоге. Дополнение «Все чаты» возобновляем после свежего каталога, поскольку в пропущенном журнале мог быть отзыв доступа. Локальные настройки можно восстановить после проверки UUID. Новый профиль получает те же серверные папки без переноса SQLite.

## События и изменения в двух клиентах

1. REST-догонка и WebSocket используют существующий журнал Messenger. У v2 создание/закрепление элемента обычно приводит к `folder.updated` со снимком папки, а удаление элемента может дополнительно дать `folder_item.deleted` с одним UUID. `folder.deleted` тоже содержит UUID. Текущий код уже понимает счётчик из части этих событий.
2. Для первого среза `folder.created/updated` ставят отметку о сверке. Явное удаление убирает папку с элементами или один элемент сразу. Отзыв доступа убирает разговор из проекции, а архивирование, восстановление и изменение состава каталога запускают сверку. Отметки, изменения и курсор события фиксируются в одной транзакции. События догонки накапливают работу до `ready`. Повтор события ничего не добавляет.
3. После `ready` объединяем обновления по владельцу и UUID папки. Запускаем не больше одного запроса по одной области одновременно. Сверку всего списка используем, когда область неизвестна. Событие во время запроса оставляет отметку на следующий проход. Явное удаление, отзыв доступа и сброс сразу повышают ревизию и блокируют запись начатого ранее ответа. Обычное уведомление о необходимости сверки сохраняет отметку, пока её не покроет новый запрос. Так поток изменений счётчиков не блокирует первую публикацию. Отметки лежат на диске и переживают перезапуск. REST-сверка сама курсор не продвигает. Прямое применение полных событий можно добавить после проверки границы между снимком и журналом и замера нагрузки.
4. Команды Core используют `POST /folders/`, `PUT/DELETE /folders/{uuid}`, `POST /folder_items/`, `DELETE /folder_items/{item_uuid}` и `POST /folder_items/{item_uuid}/actions/{pin|unpin}/invoke`. Добавление передаёт `folder_uuid`, `stream_uuid` и `chat_type`. Закрепление и удаление связи принимают UUID элемента именно текущей папки. В v2 повторное добавление того же разговора дедуплицируется в пределах папки. Для добавления и закрепления Core принимает ответ с элементом или снимком папки. При успехе или неизвестном исходе команда оставляет отметку для сверки. Создание принимает заранее выбранный клиентом UUID. Если ответ потерялся, сверяем результат, а при повторе создания используем тот же UUID, название и цвет.

## Порядок реализации и приёмка

| Этап | Готово, когда |
| --- | --- |
| 1. Подтвердить контракт | На выделенном Workspace получены обезличенные примеры списка и одиночной папки с личкой, приватной группой и каналом. Проверены пагинация, фактическая форма ответа и события для CRUD, состава, закрепления и смены доступности. Уточнено, когда после ответа команды появляется свежая проекция, и чем API отличает удалённую папку от устаревшего снимка. |
| 2. Снимок и SQLite | Через штатный адаптер Core загружает несколько страниц, строит список по каталогу и восстанавливает полный снимок из временного профиля. Проверены пустой кэш, пустая папка, пропуск страницы из-за сбоя, неизвестный разговор, приватная группа и два владельца с одинаковыми системными UUID. |
| 3. Синхронизация | REST-догонка и WebSocket дают одинаковый итог после дубля, разрыва, истёкшего курсора и перезапуска между записью курсора и сверкой. Запоздавший ответ не возвращает удалённое и не проходит после выхода. Счётчик Dock продолжает обновляться, а активный и пассивный счётчики сверяются с сервером. В логах виден путь от события или команды до фиксации и публикации без токенов и названий папок. |
| 4. Команды и второй клиент | Создание, название и цвет, удаление папки, добавление и удаление разговора, независимые закрепления сходятся в двух клиентах. Проверены потеря ответа, повтор, удалённая другим клиентом папка, архивирование, восстановление и отзыв доступа к разговору. Команды архива идут отдельным сценарием Messenger. |
| 5. GPUI | Подключить переключение папок и бейджи к снимку Core. Затем добавить управление папками, действия строки, поиск в своей и других папках, быстрый выбор папки и настройки панели. После интеграции проверить выбор и исчезновение папки, переход из поиска, клавиатуру и смену аккаунта. |

Критерий готовности фундамента — этапы 1–4 проходят через обычные точки входа Core. Для правил состава и порядка достаточно тестов Core, для курсоров и частичных ответов используем loopback REST/WS, для перезапуска — временный SQLite-профиль. Приёмка на стенде проверяет, что папки пользователя переживают выход и новый профиль, а настройки сайдбара остаются локальными.

## Что проверено

- На выделенном Workspace проверены заголовок пагинации, вложенный состав, команды с двумя независимыми сессиями и изоляция второго пользователя. Архив скрыл разговор в папках, восстановление вернуло его, отзыв подписки убрал доступ. REST и WebSocket дали совпадающие события. Снимки `folder.created/updated` содержали полный состав, события удаления — UUID.
- Два экземпляра Rust Core с разными профилями получили исходные папки и увидели создание с повтором того же UUID, переименование и очистку цвета, добавление без дублей, закрепление, открепление и удаление. Синтетические папки, связи и канал после проверок удалены.
- Loopback с обычным Runtime покрывает несколько страниц, сохранение старого снимка при сбое, удаление во время запроса, догонку после обрыва и повторное открытие SQLite. SQLite-тесты покрывают сброс курсора, защиту от отзыва доступа, откат при ошибке записи курсора и изоляцию владельцев.
- На стенде создание приватной группы без собеседника отклонено сервером. Чтение связи с типом `group` покрыто фикстурой Core.
