# Workspace для iOS

План первого прототипа. Пользователь входит в Workspace на iPhone, выбирает проект, открывает существующий личный чат и читает историю. Прототип проверяет, как нативные экраны SwiftUI работают с общим Rust-ядром. [Архитектура ядра](../workspace-desktop-architecture.md) · [Дорожная карта](../workspace-desktop-roadmap.md)

## Макеты

Экраны и особенности мобильного интерфейса сверяем со страницей «design макеты (mobile)». Другие страницы того же файла используем для общих компонентов и состояний, которых нет в мобильных макетах. [Мобильные макеты Workspace в Figma](https://www.figma.com/design/VmfwiIV4fW8gHfU3AhCZGZ/Exordos-Core--Copy-?node-id=12052-49)

## Первый сценарий

Для первого среза берём одну тестовую организацию, один аккаунт и существующий личный чат с текстовой историей.

1. Пользователь вводит логин и пароль. Если IAM запрашивает одноразовый код, появляется соответствующий шаг. После выбора проекта ядро завершает вход. При сбое пользователь видит ошибку и может повторить попытку. [Вход и выбор проекта](../features/foundation/accounts.md#auth-002)
2. Открывается список чатов выбранного проекта. Экран показывает загрузку, пустой список и ошибку с повтором. Пользователь нажимает строку чата и получает экран истории на всю ширину. Кнопка «Назад» возвращает его к списку. [Каталог разговоров](../features/messenger/navigation.md#msg-nav-001)
3. Чат показывает последние сообщения. При прокрутке вверх догружается предыдущая страница, а видимое сообщение остаётся на месте. Ответ от чата, который пользователь уже закрыл, не меняет открытый экран. [История и прокрутка](../features/messenger/history.md#msg-hist-006)
4. Новое сообщение появляется в открытом чате один раз. После возврата клиент проверяет подключение и при необходимости восстанавливает его с догрузкой пропущенных событий от последнего сохранённого курсора. [Переподключение мессенджера](../modules/runtime.md#трей-сон-и-пробуждение)

Отправка, вложения, каналы и темы, переключение аккаунтов, E2EE, пуши, звонки и публикация сборки относятся к следующим этапам. Порядок этих работ определим после проверки первого сценария.

## Границы ядра и клиента

| Слой | Чем управляет |
| --- | --- |
| `workspace-core` | Входом и сессией, проверкой доступа, запросами к Workspace, каталогом, историей, SQLite-кэшем и курсором синхронизации. Начальный запуск опирается на существующий `bootstrap`. |
| Интерфейс для Swift | Передаёт команды и события жизненного цикла в ядро. Возвращает данные для экранов, изменения каталога и истории и типизированные ошибки. Связывает операции и подписки с контекстом, поколением сессии и сроком жизни запроса. |
| Приложение iOS | Показывает экраны SwiftUI, ведёт навигацию и состояние экрана, отвечает за жесты, фокус и прокрутку. Подключает каталог данных в контейнере приложения и системное хранилище секретов. |

Для входа переиспользуем `Auth::begin_login` и `Auth::complete_login`, для списка — каталог `core::bootstrap`, для истории — `open_latest_history` и существующий путь догрузки. Сессия, проверка доступа к разговору и журнал синхронизации остаются за текущими владельцами. [Авторизация](../modules/auth.md) · [Запуск](../workspace-desktop-architecture.md#bootstrap) · [Открытие и догрузка истории](../modules/storage.md#открытие-и-догрузка)

### Обмен между Rust и Swift

Начинаем со снимка каталога и страницы истории. Догрузка передаёт добавленную часть и состояние края, обновления при открытом чате передают новые и изменённые строки. Используем те же UUID, что и в ядре. Состав полей ограничиваем данными, нужными экрану.

Сейчас `load_older_history` возвращает всё окно, включая уже показанные сообщения. При проектировании мобильного API проверяем, где вернуть добавленную часть без повторной передачи всего окна. Хранение окна и проверки доступа остаются в ядре. Экран SwiftUI применяет результат на главном потоке и удерживает позицию при вставке строк. [Текущий код догрузки](../../../crates/workspace-core/src/messenger/history.rs)

Связываем ответ с текущим экраном и поколением сессии. Уход с экрана освобождает его подписки и отменяет запрос, где это возможно. Если результат успел прийти, экран проверяет его актуальность перед применением. Проверка поколения при записи в кэш остаётся в ядре. [Контракт маршрута разговора](../modules/messenger.md#маршрут-разговора)

SwiftUI выбран для прототипа. Первый кандидат для вызова Rust из Swift — UniFFI. Версию биндингов, формат упаковки библиотеки и минимальную версию iOS определим на пробной сборке. [UniFFI](https://mozilla.github.io/uniffi-rs/latest/) · [Цели iOS в Rust](https://doc.rust-lang.org/stable/rustc/platform-support/apple-ios.html)

### Сворачивание, возврат и хранение

- Оболочка iOS сообщает ядру о переходе приложения в фон и о возвращении на экран. Ядро управляет соединением, сохранением состояния и восстановлением. iOS может приостановить процесс после сворачивания, поэтому возврат опирается на сохранённые данные и курсор. [Жизненный цикл iOS](https://developer.apple.com/documentation/swiftui/scenephase) · [Фоновое выполнение](https://developer.apple.com/documentation/xcode/configuring-background-execution-modes)
- При возврате ядро проверяет состояние сессии и восстанавливает поток событий через существующую догрузку. Данные и курсор фиксируются вместе. Повторный сигнал возврата не создаёт второе соединение для того же контекста. Общую реакцию на потерю соединения и восстановление можно использовать и в Desktop. Сигналы ОС и момент запуска восстановления определяет оболочка. [Контракт синхронизации](../modules/runtime.md#запуск-переподключение-и-остановка)
- SQLite и правила работы с кэшем остаются в Rust. Каталог базы передаёт приложение iOS. Черновая сборка для проверки связи с ядром может держать сессию в памяти. Для восстановления входа после полного завершения приложения подключаем iOS Keychain через `SecretStore`. Токены доступа остаются в памяти ядра. [Хранение сессии](../modules/auth.md#хранение-и-восстановление) · [Контракт `SecretStore`](../../../crates/workspace-core/src/auth/contracts.rs)

## Порядок работы

| Этап | Результат и проверка |
| --- | --- |
| 1. Собрать пробное приложение | Один экран SwiftUI вызывает операцию `workspace-core`. Проверяем сборку для симулятора и отдельную сборку под iPhone. Фиксируем команды, форматы и версии инструментов, с которыми это воспроизводится. |
| 2. Пройти вход до каталога | На тестовом стенде войти в один аккаунт, выбрать проект и увидеть существующий чат. Проверить ошибку входа, повтор и шаг OTP на аккаунте или тестовом ответе, который его требует. Секреты берём из локальной тестовой конфигурации по правилам репозитория. |
| 3. Открыть историю | Открыть личный чат, прочитать первую страницу, догрузить сообщения сверху и вернуться к списку. Проверить сохранение позиции, отмену при уходе и повтор после сетевой ошибки. |
| 4. Получить новое сообщение и восстановиться после фона | Второй тестовый аккаунт отправляет сообщения, пока iOS-клиент открыт и пока он свёрнут. Проверяем, что после возврата пропущенные сообщения видны один раз. Для варианта с Keychain отдельно проверить вход после полного перезапуска и выход из аккаунта. |
| 5. Снять замеры на iPhone | В Release-сборке отдельно измерить передачу страницы и время до появления читаемой истории. Проверить догрузку длинного чата и обновление при входящем сообщении. Записать модель iPhone, версию iOS, число сообщений и размер буфера, медиану и p95. |

Проверяем общую логику ядра на подставном источнике. Симулятор нужен для сборки и пользовательской цепочки. Жизненный цикл, восстановление и задержку проверяем на физическом iPhone. Операции открытия, догрузки и восстановления связываем через `op_id`. Пароли, токены и текст сообщений в журналы не попадают. [Правила диагностических журналов](../workspace-desktop-architecture.md#диагностические-журналы)

## Что показал замер на Mac

23 ноября 2026 года на Mac M3 Pro замерили вызов Rust из Swift через сгенерированные биндинги UniFFI 0.31.2. Использовали оптимизированные сборки и синтетические записи с четырьмя UUID, метками времени и текстом. Время включает создание буфера в Rust и объектов из него в Swift. Чтение SQLite, сеть и отрисовка были вне замера. Размер — объём буфера в памяти процесса.

| Размер списка | Буфер | p95 времени по прогонам |
| --- | ---: | ---: |
| 50 сообщений по 1 КБ текста | 60 КБ | 0,42–0,59 мс |
| 50 сообщений по 4 КБ текста | 214 КБ | 0,28–0,82 мс |
| 500 сообщений по 1 КБ текста | 599 КБ | 2–4,5 мс |
| 2 000 сообщений по 1 КБ текста | 2,4 МБ | 13–17,6 мс |

Страница из 50 сообщений укладывалась в 1 мс в 95% замеров на Mac. Это совпадает с текущим размером страницы REST. Большие окна оправдывают передачу изменений при догрузке. Целевую задержку и расход памяти уточним по результатам запуска на iPhone.
